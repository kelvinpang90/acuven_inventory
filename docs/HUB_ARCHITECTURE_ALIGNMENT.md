# 与 Acuven Hub 系统群的架构对齐

> 版本：1.0 对齐草案 · 日期：2026-10-07。用户要求核对系统群架构并修订 Inventory 文档。只修改本项目文档，不创建共享核心、应用代码、控制面登记或其他项目任务。

## 1. 依据与优先级

- [系统群总讨论](../../acuven_hub/DISCUSSION_2026-10-07.md)：独立模块、组合门户、租户/身份/授权、CRM/AI、三种交付形态、Demo 线索及质量优先。
- [商品与库存修订](../../acuven_hub/REVISED_PRODUCT_STOCK_ARCHITECTURE_2026-10-07.md)：明确取代总讨论里商品主档切换、两套库存、POS 不能单卖等旧规则；是本次商品和数量归属的优先依据。
- [开发优先顺序](../../acuven_hub/DEVELOPMENT_PRIORITY_2026-10-08.md)：讨论级依赖路线，不是现有 Shop/OpenClaw 任务的实施授权。

以上文件均为讨论/设计资料。已确认产品选择可写入需求；`acuven_stock_core` 独立常驻服务的部署边界已经确定，具体数据库拓扑、API、原子事务和迁移实现仍待设计验证。原 Inventory 的自营试点业务参数继续适用，不能将新产品架构解释成所有未来客户采用相同缺货风险或配置。

术语：**Acuven Hub** 表示系统群/可选统一门户；**Inventory** 表示多渠道库存产品；**Core** 表示共用商品目录与基础库存账。当前文档不再用 Hub 作 Inventory 的别名。引用历史讨论中的 Hub 时按历史语境解释。

## 2. 必须修订的差异

| 旧 Inventory 设计 | 新架构要求 | 本次修订 |
| --- | --- | --- |
| SKU 身份与余额/流水在 Inventory 本项目库内权威写入 | 一份随相关模块交付的商品目录和基础库存账 | 商品身份、O/H/C/U、预留和基础流水由 Core 管；Inventory 管映射、政策、发布和对账。 |
| ERP 只接 Inventory 的另一本库存结果 | ERP、Shop、POS 单模块与组合复用同一基础账 | ERP 的采购/自身销售通过 Core 记一次；加购 Inventory 增加跨入口能力，不新建第二账。 |
| 单卖网店使用另一套简易库存，再迁移 Inventory | 任一相关模块随附相同版本化库存核心 | 单模块就用 Core；增购尽量复用原 ID、流水、未结引用。已有分离实例/库存池仍需合并迁移核对。 |
| 单自营、多租户/部署模式待考虑 | SaaS、托管专属、客户自托管均为产品目标 | 首个真实验证仍自营，但身份/租户/池和部署契约先设计；外部生产前各形态独立验收。 |
| CRM/ERP 都只按外部系统对接 | Acuven 自家模块间共享核心；客户外部系统用适配器 | 保留外部接入协议，不强迫 Acuven ERP 经过库存快照双向同步。 |
| 一个 SKU 一个全局库存数 | 同商品身份可属于不同库存池/地点 | 不同池不互借；本次 V1 先一个地点/池，数据键/授权不写死为全系统唯一。 |
| Shop/ERP/POS 多入口未体现模块授权 | 两个销售入口共卖一批货需 Inventory | 已购模块、入口注册、库存池归属及共享授权在业务端执行。 |
| 一个共用 Demo 账号直接体验 | 联系方式登记后体验，线索独立保存至 CRM | 共用示例保持可重置，真实线索不进 Inventory 模拟库、不随重置删除，不默认营销。 |
| 约一个月/固定上线日期 | 质量与功能完整优先，不设总完成日期 | 替换旧日期承诺，按阶段证据推进；审批和计费现有开发可并行。 |

## 3. 分层及数据所有权

| 层 | 拥有的数据/业务 | Inventory 的关系 |
| --- | --- | --- |
| 商品身份目录 | 每租户稳定商品/规格 ID、SKU、条码、基本名称、参考售价、版本/审计 | 编辑入口可在 Inventory，但调用目录 API；本项目不维护另一份可编辑身份主档。 |
| 基础库存账 | 每租户/库存池/地点/规格的实物、预留、销售占用、不可售、最小事实、流水及数量幂等 | Inventory 命令/事件通过账 API 应用，查询权威版本；本地缓存不能覆盖账。 |
| Inventory 产品 | 渠道映射/份额政策、安全库存政策、分配比例、平台授权/能力、库存发布、转移、差异待办/核对 | 多入口跨渠道附加能力；单卖随附目录和基础账，不依赖购买 ERP/门户/AI。 |
| ERP | 采购/收货单、供应商、仓管流程、成本及经营单据 | 与同一 Core 读写已核实数量事实，销售/出库只记一次；单据与成本继续 ERP 管。 |
| 网店/POS | 各自商品展示、渠道价格、原始订单/交易、支付、售后；POS 另有设备离线额度 | 单卖随附 Core；多入口共卖一池时接 Inventory 的政策与协调。 |
| Acuven Hub 门户 | 组合入口、租户/账号映射、模块授权、跨系统视图/待办、集成状态 | 可调用 Inventory 授权 API，业务端重验权限；门户失联不成为本地业务强依赖。 |
| CRM/AI | CRM 客户主档/同意；AI 工具编排、查询及授权建议 | 不拥有库存数量；高影响库存调整展示变化并由有权人员确认。 |

[`acuven_stock_core`](../../acuven_stock_core/REQUIREMENTS.md) 已确定为独立常驻服务，目前没有应用代码。它持有商品目录与唯一基础库存账，Inventory 通过版本化 API 调用；具体进程配置、数据库拓扑、升级方式仍需设计。产品共用核心不授权多个业务仓库跨库写表。

## 4. 套餐与库存池规则

| 组合 | 同一库存池的合法销售入口 |
| --- | --- |
| 只买 Shop、POS 或 ERP | 该模块一个销售入口；商品目录/基础账随附，不须买 Inventory。 |
| ERP + Shop，无 Inventory | Shop 可销售；ERP 可采购收货。ERP 自身再从同池卖出构成第二入口，需 Inventory。 |
| ERP + POS，无 Inventory | POS 可销售；ERP 收货不算新增销售入口。 |
| Shop + POS，无 Inventory | 可以同商品身份各卖不同实物池；不得默认共享同一批货或互借额度。 |
| 已有 Inventory 的多入口组合 | 配额/协调在同一基础账上生效，逐入口去重与核对。 |
| Inventory 单卖 | 随附目录与基础账，接已实现获权渠道，客户无需购买 ERP 或门户。 |

“两个销售入口”按同一库存池的实际销售来源识别，不仅看仓库数/套餐数。ERP 采购是入库来源，不增加销售入口；多个设备离线额度由 POS 在所属池内隔离，跨销售入口额度是 Inventory 能力。

模块授权属于商业平台契约，库存和产品 API 仍执行已购能力边界。建议模块独立部署使用可本地核验的授权配置；联邦登录保留本地账号/角色映射，未知租户、失效凭据或无授权的新动作不默认放行。授权缓存、收紧/撤销生效和离线规则须评审，不能为门户可用性要求免鉴权。

## 5. 原子预留与配额：必须先设计的技术闸门

原稿把余额、Q/T、预留及幂等置于 Inventory 单库事务；迁至 Core 后，不能在 Inventory 先减 Q、另一 HTTP 请求才加 H，失败会留下两边数量不同步。

建议：Inventory 拥有跨入口政策及期望版本，Core 在唯一数量事务内校验**已确认生效的政策/入口额度、余额、预留、稳定业务引用**，同时保存执行计数、H/C 和基础流水。Inventory 保存政策目标、Core 接收/生效状态与外部平台发布结果；读本地目标不能视作账内已生效。Core 的约束执行记录不构成第二份数量账，也不把连接器/平台密钥放入 Core。

Core 应发布同事务 outbox 的变化事实，Inventory 消费后更新对账视图及渠道发布任务。响应丢失查 Core 原请求/业务引用，不复建预留；批量事实全部应用或全部不应用。Qty、预留有效期、最后一件并发、Q/T 转移、安全库存提高、外部销售不足的需求记录沿用 STOCK_RULES 业务语义。

这是实现建议，正式 Core 契约、额度约束事务边界、幂等作用域和恢复链未完成，相关 Inventory 写入任务不得 ready。需在 Core 仓库验证 MySQL 并发，再从 Inventory API 验证包装层；单模块直接 Core 路径与多入口 Inventory 路径不能各写一次同一事实。

## 6. 商品身份及渠道内容

每租户一个逻辑目录，组合客户读同一商品/规格 ID。Inventory 原 sku_id 在设计 v1 中统一解释为目录规格 ID；外部商品/规格 ID 与代码对照仍由 Inventory 管。参考售价由目录维护，不要求 Inventory 将价格放入库存事件。

渠道图片、营销文案、实际售价、优惠及平台专有属性在对应渠道；参考价变更只形成受控待确认建议，不自动改价。Inventory 商品管理页可管理目录基本身份，完整外部商品上架和自动图片/分类/价格发布保持未承诺状态。

历史订单保存当时身份/商品/成交价快照在原交易系统，Core/Inventory 保留稳定来源及数量引用。不同客户、不同池中相同 SKU 代码不表示可共享库存。增购原实例复用 ID，独立环境合并需一次显式映射/盘点/未结处理，不能凭名称或单纯同 SKU 自动合池。

## 7. 租户、门户和支持权限

SaaS 业务对象、连接、映射、余额引用、库存池、预留、事件、幂等、队列、缓存和审计均绑定可信 tenant 上下文；连接/池/地点由后端已验证身份及配置确定，正文不自选 tenant/pool 绕权限。首次自营也是一个明确租户。

商品和基础账请求还校验核心实例/租户/池/地点/规格及动作；Inventory 管理员拥有某租户权限不等于可改其他池或核心实例。门户 JWT/登录映射只是身份来源，业务端同时重验角色、已购能力、对象与版本。外部客户数据默认不向 Acuven 平台运营管理员开放；限时支持 grant 要有客户授权、范围、期限、撤销和审计。

Inventory 对外保留独立入口、本地登录和 API。产品三种交付形态分别验收数据/资源隔离、升级、远端备份、密钥归属、支持访问与退出导出；共享主机不等于已满足 SaaS。单自营 V1 通过不代表外部多租户生产已通过。

## 8. ERP 和 CRM 的对齐

自家 ERP 收货调用同一基础账，账入一次，ERP 关联入账结果；ERP 自身销售若与 Shop/POS 同池共卖，需启用 Inventory 跨入口能力。Inventory 不再将本项目私人数量账复制给 Acuven ERP 作为唯一运行方式。客户外部 ERP 仍可用独立适配器和映射，实施时确定该库存范围唯一写入入口。

数量变更/基础流水由 Core 出站事件或受限查询提供，ERP 停机不让已启用的 Inventory/账网络等待而锁住库存事务。若 ERP 同步需适配器，目标/应用结果仍持久重试；ERP 原有库存写入在迁移切换点停用或改经 Core。

Acuven 自用经营单据采用**按日、按渠道汇总销售记录**，原逐笔订单及金额留 Shop/平台。该经营汇总须从授权交易源取得金额/退款引用，在 ERP/所属集成中形成；Inventory 仅供数量及稳定来源引用，不新增金额/发票/完整订单字段。汇总不能再次扣库存；付款日/发货日等汇总口径和正式票据仍待对应项目设计，本次不重开已撤回问题。

CRM 负责统一客户主档和营销同意/退订。Inventory 不存完整顾客信息；Demo 联系登记通过独立真实线索流程进入 CRM，线索与重置示例库隔离，只跟进访客主动咨询或报价。旧 WhatsApp 号码共用方案与系统群生产渠道规则存在潜在差异，需要在客服项目核对实际渠道/租户方案；本次不改号码或发送消息。

## 9. V1 与产品后续范围

第一运行样例仍为 Acuven 的单地点/单池、少于 100 规格、默认安全库存 2、自营 Shop/Shopee；TikTok 按独立获权情况接入。既有人工 Shopee 份额、每天两次核对、严重告警、故障收款和退货规则是该试点配置，不能写成所有租户全局默认。

数据与核心契约预留 pool/location/tenant；多仓业务、跨地点调拨、POS 设备离线额度、门店退货和冲突需要后续专门设计。POS 单卖的设备额度由 POS 与基础账实现；Inventory 的跨入口份额另行验收。数据里有 location_id 不表示已经交付多仓/POS。

商品目录和基础账、既有 ERP/Shop 数据迁移、租户/模块授权契约先于 Inventory 数量写入实现。开发方向为：完成现有 Shop Demo，同时定义 Core 契约 → 实现独立 Core 并接单渠道真实 Shop → Inventory V1 → 获权 Shopee → ERP 实用 → 后续 POS/统一门户。CRM/AI 样板可在不依赖 Core 的隔离环境并行推进。优先顺序是文档规划，不改现行任务；各阶段质量验收先于日期。

## 10. 对齐验收与未完成闸门

| 验收 | 所需证据 |
| --- | --- |
| 商品身份唯一 | ERP/Shop/Inventory/POS 入口读同一目录 ID，基本名称/条码一处变化；渠道价/图片不被覆盖。 |
| 数量账唯一 | ERP 收货、Shop/平台销售、取消/返库到同一本 Core 账；没有私有 Inventory/ERP 再扣一次。 |
| 加购与合池 | 同原实例增购不重建流水；分离实例/池显式核对基线、未结与切换/回退。 |
| 套餐边界 | 单卖附基础核心；未购 Inventory 的两个入口不能共卖/互借同一池，ERP 收货不误计销售入口。 |
| 权限 | A 租户无法查/改 B 的映射、池、预留、事件；门户/支持/AI 不绕过模块授权。 |
| 故障 | AI/门户/ERP 暂不可用时本地合法业务继续；Core 故障按明确库存策略处理，不伪造版本/预留。 |
| 原子性 | 最后一件并发、Core 超时响应丢失、政策未生效、Q/T 及补交乱序均不产生第二占用。 |
| Demo | 登记线索独立 CRM 存储，共享示例重置不删线索或影响生产，默认不营销。 |

待细化：独立 Core 的 API、数据库与故障域部署细节；ERP 现有多维状态/成本的兼容映射；渠道政策在 Core 的原子执行；SaaS 隔离及本地/联邦授权；已有分离数据迁移与恢复；POS 后续额度。没有这些技术证据时只能保持设计/待登记状态，不能把架构对齐作为代码就绪或已支持第三方连接。
