# Acuven Inventory：需求文档

> 版本：1.0 草案 · 日期：2026-10-07 · 状态：按 Acuven Hub 修订为共用商品目录/基础库存账与 Inventory 多入口产品；核心、迁移及数量接口尚待评审。
> 本文记录本次访谈的目标；平台应用 API 权限、支付账户持续可用性和真实交易链路、物流商资格仍须逐项核实，不代表已接通。

项目名称为 **Acuven Inventory**，项目 ID `acuven_inventory` 尚未登记。Acuven Hub 是系统群/可选门户；Inventory 是多入口库存产品；Core 是随相关模块交付的商品目录与基础库存账。本文按[系统群架构对齐](HUB_ARCHITECTURE_ALIGNMENT.md)修订，商品/数量主题以[商品与库存修订](../../acuven_hub/REVISED_PRODUCT_STOCK_ARCHITECTURE_2026-10-07.md)优先，原日期和私人库存账方案已被取代。

阅读顺序：本文说明业务目标与已确认选择；[开发设计](DEVELOPMENT.md)说明系统边界；[库存规则](STOCK_RULES.md)与[API 契约](API_CONTRACT.md)细化数量和接口；[交付计划](DELIVERY_PLAN.md)与[运营设计](OPERATIONS.md)说明跨项目任务、界面、重置和恢复。新增技术细节是可评审的建议，不冒充已经由用户逐项确认或已经实现。

## 1. 产品目标

Inventory 是可单卖的多销售入口库存控制产品，管理渠道规格映射、安全库存/份额政策、库存发布、最小销售事实、差异与对账。随产品交付共用商品身份目录及基础库存账；实物/预留/销售占用和基础流水由该唯一账处理，Inventory 不另建第二数量账。第一真实验证仍为 Acuven 单地点/单池、自营 Shop/Shopee，TikTok 按独立获权情况接入；首期不提供完整订单、资金和物流后台。

产品面向多租户 SaaS、Acuven 托管专属、客户自托管三种形态，模块可独立交付；V1 的真实验证范围先为 Acuven 自营，外部客户/多仓/POS 生产分别验收。Lazada 后续接入。已获批且可用的渠道先上线，不等所有平台。Acuven 另需一个供顾客体验的 Demo 独立站；已确认与真实站共用代码，但分别部署并使用完全分离的数据和外部账号。真实站继续负责自己的真实下单、在线支付和履约。

**首要任务：推进 Shopee 与 TikTok Shop 的开发者准入、应用权限和自营店授权。** 两家自营店铺均已开通，属于同一马来西亚经营主体；Shopee 已有真实订单，TikTok Shop 暂无订单。2026-11-21 起先走自营卖家开发者路线，第三方申请条件满足后继续（acuven_hub `DECISIONS.md` C-20）；第三方资格不代表多商户功能已经上线。两个平台的审核意见、资格问题与当前状态是经营信息，记在 acuven_hub 私有仓库的 `inventory/ACCESS_APPLICATIONS.md` 与 `inventory/TIKTOK_REJECTION_REVIEW_2026-10-08.md`，不放进本公开仓库。真实 HTTPS 授权回调仍待部署，两家应用创建、库存权限及店铺授权均未核实完成。Lazada 保留为下一阶段，不阻塞首批上线。基础平台设计和开发可与审核并行；已可用的渠道和独立站先上线。

## 3. 用户与权限

- **Acuven 库存管理员**：盘点、调整库存、设置安全库存与渠道配额、管理渠道连接及处理差异。
- **Acuven 运营员**：查看同步状态、差异和异常，提出核对及调整建议；首期不能直接修改库存数量、安全库存或渠道配额，也不能查看或修改平台密钥。
- **顾客**：先登录对应独立站账号，才可通过 AI 客服查看或操作自己的订单；未发货时可请求改地址或取消，退款申请须由人工审核。市场平台顾客按各平台的身份与隐私限制处理。

首批自营部署仍需让每条渠道连接明确归属 Acuven，外部事件以“平台 + 店铺 + 事件 ID”去重。SaaS 是已选产品形态，租户隔离/本地与联邦身份/模块授权需先设计；不得把单商户试运行称为多租户已验证。支持人员需客户限时授权才可访问外部客户业务数据。

## 4. 关键业务流程与验收

### 4.1 商户及店铺接入

1. 先按第三方开发者类别申请 Shopee 与 TikTok Shop 的开发者权限；首批授权连接的仍是 Acuven 自营店，Lazada 暂不作为首批上线条件。
2. 获批后由自营店铺授权连接，保存授权状态、店铺标识、获批范围与有效期；失效时告警并停止自动写入。
3. 平台只批准部分接口时，已获批且经验证的功能可分阶段开放；后台逐项标明可用、待批准或不可用。缺少库存写入或销售变动事件能力时，不得标示为“真实库存自动同步”，也不得自动分配会产生未核对销售风险的跨渠道库存。
   在渠道仍实际销售、但其销售事件无法自动进入 Inventory 的阶段，必须把该渠道实际在卖的 SKU 与独立站库存隔离。Shopee 的已选方案是在卖家后台为每个共享 SKU 设置固定份额，Inventory 为真实 Shop 留独立份额；两个份额合计加安全库存、不可售与已知销售占用，不能超过盘点实物在库数。未连接渠道的剩余展示量不得被 Inventory 当作可自动回收的库存，页面标为“人工配额/待接入”，不得显示“实时同步”。TikTok Shop 尚无订单；其接口未就绪且尚未启动真实销售时配额为 0，若先开始销售，须先执行相同的人工隔离或暂不在 Shop 销售相同 SKU。
4. 导入渠道商品规格和现有可售量，盘点实物后确认中心 SKU 映射、期初数量、安全库存与渠道配额，之后才开启自动写库存。
5. 上线切换时可短暂暂停各渠道销售。停售窗口内盘点实际仍在仓内的实物，并按 SKU 登记各渠道已售但尚未发货的订单占用数量，核对初始安全库存与配额，再逐渠道恢复销售。保存每个店铺的切换时间与订单处理进度，旧订单补拉只能补齐缺项，不能重复占用库存；核对通过后才开启该 SKU 的自动同步。
6. 某平台未获批准时页面显示“待开通”；仅获部分权限时，页面显示可用功能及缺项，不声称未验证的库存同步已启用。
7. 新平台接口获批后，管理员完成权限、SKU 映射、期初占用、安全库存、配额及库存读写核对，当天核对通过即可启用全部已确认 SKU 的库存写入，不要求先运行 3 天或 7 天只读观察。按 SKU 记录成功、失败或结果未知；未完成核对、存在差异或未确认写入结果的规格不算已接通，进入人工处理。

**Shopee 人工配额过渡流程**：只要 Shopee 共享 SKU 仍在售，Acuven 管理员每天至少两次（包括周末和节假日）在卖家后台核对新销售、未发货、取消、实际出库及展示库存，按稳定的订单行标识、SKU、数量、动作和发生时间向 Inventory 登记最小库存事件；不复制买家资料。每次核对记录执行人、时间、对账区间、核对数量和差异。卖家后台配额不得超过为 Shopee 隔离的剩余额度；不得因为接口缺失而把 Shopee 未售完的份额自动转给 Shop。漏做当次核对时，仅在后台显示逾期及未核对区间，不发 Telegram 消息；停止增加该 SKU 在其他渠道的配额，但两个渠道继续销售且系统不自动停售。用户接受核对延迟及超卖风险；逾期记录必须保留，不能把逾期视为已核对。实际核对发现数量不符、配额超限或可能超卖时，按严重库存异常规则主动提醒并处理。平台接口接通时，以最后一次人工核对时间为接管点补拉、去重和对账，再结束人工模式；旧订单不得重新占用。

**验收**：未授权店铺不能读写；撤权或令牌失效后不继续假报同步成功；重新授权后能补拉库存变动所需事件并对账。

### 4.2 商品与 SKU 映射

- 中心 SKU 是库存核算单位。每种实际可拣货的颜色、尺寸组合分配一个固定、唯一的 Acuven SKU，例如 `ACV-TSHIRT-BLK-M`；代码一旦用于库存流水，不复用给另一种实物。中心 sku_id 引用共用目录的规格 ID，身份编辑经目录 API；它可关联 Shopee、TikTok Shop 与真实独立站各自的商品规格编号；首批每笔销售的一个规格只扣一个实物 SKU 的相应件数。
- 首次接入先导入已有商品，记录平台、店铺、稳定的商品 ID、规格/变体 ID，以及平台提供时的卖家 SKU。目前两家自营店铺的商品规格基本未填写卖家 SKU，因此首批需按实物和渠道规格逐行确认对应的 Acuven SKU；商品名称、图片和价格只能辅助核对，不能单独作为自动匹配依据。也支持先建中心 SKU，再关联新上架的渠道规格。
- 确认统一 Acuven SKU 后，先核实 Shopee 和 TikTok Shop 对现有规格卖家 SKU 字段的修改规则及影响，再逐项补填该编码。补填进度与实际写入结果要记录；补填不是开启 Inventory 库存同步的前提，平台字段无法修改时仍以稳定的商品/规格 ID 映射。
- 映射和期初盘点均确认后，才对该规格开启自动库存写入。任何缺失、重复或存疑的映射进入人工核对队列，不把该规格的销售事件自动归到其他 SKU，也不发布未经核实的新增可售量。映射变更保留操作者、原因和旧/新关系；历史库存事件始终引用当时确认的实物 SKU。
- 目录维护 SKU、条码、基本名称和参考售价；各渠道维护自己的图片、营销文案、实际售价、分类、优惠、运费和支付。参考售价变化只形成管理员待确认建议，库存同步不自动改价或发布外部平台完整商品资料。
- 不支持组合装、套装或“一条渠道 SKU 对多个实物 SKU”的扣减。未映射或重复映射的商品停用自动库存处理，进入待核对队列。
- 首期同一店铺内，一个中心 SKU 只对应一个生效的商品规格／商品链接；不支持同店多个链接同时销售同一中心 SKU。不同店铺可各有一个规格映射到同一中心 SKU，并按各连接的配额销售。发现同店重复映射须先人工核对并停用多余映射，不能向多个链接分别发布同一份完整配额。
- 首期 3C 商品仅按 SKU 和整数数量核算，不逐件记录序列号；发货、退货及库存接口均采用 SKU 与数量。序列号追踪、逐件身份核验或序列号保修管理属于后续需求，当前不能声称库存流水可追溯到具体一台设备。

**验收**：同名但不同规格不会被合并；同一店铺的同一外部规格 ID 只能有一个生效映射；未经核对的规格不能自动写入库存；变更映射有审计记录，旧销售事件不被重新归到新 SKU。

### 4.3 单地点库存、配额与安全库存

- V1 先使用租户内一个默认库存池/地点。Core 按租户/池/地点/目录规格记录实物、不可售、预留、销售占用及流水；Inventory 管理安全库存/份额政策并从 Core 的已生效执行结果取得可分配量；盘点纠错、到货及实际退货入库必须留下调整流水和原因。首期不建立线下销售、送样或损坏出库的专门流程。只有 Acuven 管理员可以直接修改库存数量；必须填写原因，并保存修改前后数量、操作者和时间。
- 供应商补货按 SKU 登记实际收到的数量，生成独立入库记录和库存流水，保存入库时间、操作者与原因；到货入库采用数量增量，不以直接覆盖库存总数代替。重复提交同一笔入库不得重复增加库存。首期不建立采购单管理流程。
- 真实库存上线后每周全面核对一次实物数量与系统在库数，发现异常立即核对；该盘点不同于 Shopee 每日销售登记。实物盘点包括仍在地点内的已售未发货商品，不以渠道可售配额作为实物数量。盘点期间入库和发货不停，须记录各 SKU 盘点基准与实盘时间，以及期间实际进出数量、发生时间和来源，再核对到同一时间口径。差异由管理员核对后以流水纠正；期间变动缺失或有争议时保持待核对，不自动根据未对齐的实盘值改库存。记录操作者和更正原因，不能把实盘数直接写成可售量。
- 补货后新增可分配量按该 SKU 已设置的渠道比例自动计算各渠道新增份额，仍须遵守安全库存、配额合计、渠道权限及异常状态限制；不能把全部到货数量直接当作新增可售量。比例针对补货增量，不能自动搬走其他渠道原有份额。Shopee 尚无接口权限时，生成管理员待办；用户核对最新销售与后台库存后，手动更新卖家后台并在 Inventory 确认生效。在确认前该目标份额须保留给 Shopee，不得用于其他渠道，也不得显示为平台已生效。
- 每个新 SKU 的渠道比例由 Acuven 管理员逐项设置，不预填统一销售比例；未设置有效比例时，新增库存保留为未分配量，不触发自动增配或自动调配。尚未开始销售的渠道保持 0，启用自动分配前有效比例须合计 100%；配置修改须记录操作者、旧值、新值和时间，不直接改变原有平台展示数量。
- 库存口径必须统一：`可分配量 = max(0, 实物在库 − 不可售 − 已售未实际出库占用 − 独立站临时预留 − 安全库存)`。已发货时同时减少实物在库并解除对应销售占用，不再二次减少可分配量；未发货取消时解除占用；退款批准本身不增加实物或可售量，只有实际退货检验入库才增加实物。每次变化保留来源事件及前后数值，能从流水复算。
- 新建 SKU 的安全库存默认 2 件，可逐项改为其他非负整数。安全库存只从总可售量扣一次，再将剩余量分给 Shopee、TikTok Shop 和真实独立站；若没有可分配量，Inventory 不允许新增分配或预留。后台仍展示各平台最后确认的实际数量及可能超额，不把平台未改写的库存伪报为 0，也不自动向平台写 0。
- 首批采用固定渠道配额。配额代表某渠道还能卖出的上限，并非多份实物；正常状态下所有渠道剩余隔离份额与转移隔离量合计不得超过可分配量；提高安全库存、盘点短缺或外部超卖导致超额时，保留事实并进入差异核对，不以删除配额或占用掩盖缺口。某渠道售出后，其剩余配额相应减少，同时产生销售占用；平台已自动减少展示库存时，Inventory 不再重复扣该平台展示量。调整配额只有在平台确认写入后才显示“已生效”，失败或结果未知时保留目标值与平台已确认值的差异，并告警。首期不设低库存数量提醒阈值，是否将某 SKU 集中到一个渠道销售由管理员自行判断并调整配额，系统不自动停售。此选择不改变默认安全库存 2 件的扣除规则，也不关闭库存冲突或可能超卖告警；未连接渠道的人工份额不能自动转给其他渠道。
- 已自动接通的渠道中，某渠道剩余配额用完而其他渠道仍有余量时，允许在平台能力及核对条件满足后自动调配未售出的份额。先减少来源渠道可售量，并确认写入和相关销售变动，再增加目标渠道；减少失败、结果未知、事件未核对或映射／授权异常时不能增加目标份额。预留和已售占用不参与转移，人工配额渠道不参与自动调配。该流程属于正常配额调整，不改变异常情况下不自动停售的决定。触发后按该 SKU 配置的渠道比例重新分配参与渠道的剩余可调配库存；未接通或非参与渠道的份额保持隔离，比例为 0 的渠道不因调配而开始销售。
- 人工配额渠道的可用上限取卖家后台已核实的剩余展示量与 Inventory 记录的剩余人工份额中较小者；销售、取消及出库的人工登记与自动事件使用同一去重规则。人工登记属于库存事件而非无依据的盘点改数；只有管理员可确认登记及更正，错误登记须以反向事件留下原始记录和原因。
- 正常情况下，独立站下单前经 Inventory 原子预留库存；支付失败或超时释放预留。若结账时 Inventory 无法连接，用户决定独立站仍按普通订单收款，付款前不显示额外库存待确认提示；Shop 必须在自己的数据库中持久记录“已付款、待库存核对”的内部状态，发出紧急告警，并在 Inventory 恢复后补交库存事件和人工核对。此例外可能产生已付款但无货订单，安全库存不能消除此风险。市场平台订单事件使相应配额被占用；如果平台已自行扣库存，适配器不得重复扣该平台展示的数量。退款本身不增加可售量，实际退货经检验入库后才增加。
- 若顾客在预留过期后才完成支付，Shop 不得把支付成功等同于库存已确认；按“已付款、待库存核对”记录，补交稳定的订单行事件并人工处理冲突。正常预留转销售占用、超时释放和迟到付款之间必须幂等，不能重复扣减或凭空恢复数量。
- Shop 仅在顾客提交订单并准备进入付款页时创建库存预留；加入购物车、浏览商品或填写结账地址不占用库存。预留须由 Shop 服务端基于已校验的订单行、数量和渠道配额创建，不能由顾客浏览器直接写入。未付款预留有效期为 30 分钟，到期释放；迟到付款按已付款待库存核对流程处理。顾客可见付款期限须与服务端预留期限一致，最终支付服务商的会话关闭、付款中状态及超时处理仍需联调验收。
- 同一已登录顾客或同一访客浏览器会话，同时最多允许 3 笔有效且占用库存的未付款订单，每笔可包含多个商品。相同订单重复提交复用原订单及预留，不计作新订单；已确认付款、取消或预留到期后不再占用该未付款名额。限制由 Shop 服务端执行，不能仅依赖前端按钮。
- 已付款但未发货订单的商品规格与数量不直接修改；顾客需按既定身份核验与取消规则取消原单，再建立新订单。新单重新核算价格、优惠、运费和库存，不沿用已取消订单的预留；原单退款仍须人工审核，重新下单不能视作原单已经退款。改地址及取消订单仍按已确认的履约状态限制处理。
- 顾客进入付款页但尚未付款时，如需修改商品或数量，先确认作废旧支付会话并释放旧预留，再创建新订单和付款页；不能让旧、新付款页同时作为同一次修改的有效付款入口。支付已成功或状态未明时先核验，不能假定旧单未付款后直接释放。旧单及其关联流水保留，新单仍重新校验价格和库存。
- 同一订单包含多个商品时，正常路径下库存预留须整单成功或整单失败；任一商品库存不足，整单不进入付款页，提示具体缺货项，由顾客调整购物车后重新提交，不自动删掉商品或留下其他商品的部分预留。已明确返回库存不足与库存服务不可用须区分；已确认的故障期间继续收款例外，不适用于已知缺货或无权操作。
- 真实网店商品页及面向顾客的 AI 库存回答仅展示有货、售罄等可用状态，不展示具体剩余件数；状态依据该网店获分配份额。Shop 后端结账仍查询并校验实际可售数量，管理员后台显示完整库存及配额。顾客页面响应和客服工具输出不能携带供前端或 AI 自行隐藏的完整库存数量，也不能展示其他店铺配额。
- 平台促销、平台仓或共享库存若使库存写入受限，应标记“平台控制”，不能将本地成功当作平台可售已更新。

**验收示例**：某 SKU 实物在库 10 件、不可售 1 件、已占用 1 件、安全库存 2 件，可分配 6 件；可分给 Shopee 2 件、TikTok Shop 2 件、真实独立站 2 件。相同销售事件到达两次只占用一次。安全库存从 2 提高到 4 时，可分配降为 4 件，系统停止新增 Shop 预留与跨渠道自动增配，标记超额 2 件并告警，要求人工核对平台已展示的数量和调整渠道配额；不会自动停售平台店铺。

**补充数量验收**：正常份额约束、异常需求缺口和转移隔离量按 [STOCK_RULES](STOCK_RULES.md)核算。已确认但库存不足的销售事实保留为需求与差异，不能丢弃、自动清掉占用或强扣实物为负。预留过期/未发货取消优先恢复原连接份额，不能恢复的部分保持未分配或待核对；实际可售退货、盘点正差及安全库存降低先进入未分配量，补货才按已设置比例自动分配。不可售退货增加实物及不可售量，不增加可售量。按订单行限制累计取消、出库和返库，重复及乱序不重复改变余额。

### 4.4 最小销售事件与异常处理

- Inventory 只保存足以改变库存和防止重复处理的信息：来源平台、店铺、外部事件/订单行标识、中心 SKU、数量、库存动作、时间和处理状态；不做完整订单列表、支付、收货地址、运单或退款审批。
- 各平台/Shop 是自身订单状态的权威来源。Inventory 用官方事件与补拉确认“新销售占用、未发货取消释放、已出库确认、实际退货入库”等库存动作，处理重复、乱序和漏事件。
- 授权失效、库存写入失败、映射不明或对账差异时，停止受影响 SKU 的自动增配并立即告警，但首期**不自动停售任何渠道**，也不自动把平台库存改为 0。真实独立站在 Inventory 仍可用时继续尝试正常预留；Inventory 不可用时按上述例外继续收款，并把订单列入人工核对队列。运营负责人根据告警决定是否手动停售、改配额或恢复同步；界面须明确显示持续销售带来的超卖风险。
- 如果运营人员直接在 Shopee 或 TikTok Shop 后台修改了库存，造成该商品与 Inventory 数量不一致，标记该商品待核对并告警，暂停其自动同步；不得把平台改动自动视作新的实物库存，也不得未经确认用 Inventory 数量覆盖平台。运营员可核对实物、未发货占用和平台当前可售量并提出建议；只有 Acuven 管理员可确认会改变库存数量或配额的调整并恢复同步。异常期间不得自动增加该商品的可售配额。
- 超卖时由 Acuven 运营人员核对实物及已确认销售，按来源平台的真实确认时间与已承诺状态决定履约顺序；无法履行的由原销售渠道负责联系顾客及处理替代、等货或退款。对独立站故障期间已付款但无货的订单，在发现缺货后 48 小时内由人工联系顾客处理。Inventory 只记录库存差异及处理结果。

**验收**：正常路径的并发预留不能使可售量为负；重复事件不重复占用；连接异常可看见、可补拉并对账。故障路径须验证 Shop 在 Inventory 不可用时仍能保存已付款订单和待核对记录、触发告警、恢复后不重复扣减，并把缺货订单交人工处理。由于平台同步异步且用户选择故障时继续销售，不承诺绝对零超卖。
Shopee 人工过渡另须验收：同一 SKU 在 Shopee 卖家后台与 Shop 各有不可互借的固定份额；后台能显示上次人工核对时间、下一次待办及逾期；重复登记不重复占用；核对差异阻止自动增配并告警；接口获批后补拉不重复登记既有销售。每日两次核对只能降低滞后风险，不构成“实时同步”或“零超卖”承诺。

### 4.5 Acuven Shop 改造

现有 `acuven-shop` 的需求规定模拟商品、支付、发货、退款和每日库存重置。用户需要同时保留一个可展示给顾客的 Demo 和一个真实运营的独立站。已确认**同一代码库、两个独立部署**：演示站只用演示数据与模拟支付；真实站使用独立数据库、真实商户支付账号和 Inventory 库存，不执行每日演示库存重置。生产站不能用运行时页面开关一键切成 Demo。

- Shop 自己负责商品售价、优惠、运费、币种、税费/发票设计、顾客账号、真实订单、在线支付、物流与售后；Inventory 只提供 SKU 映射、可售查询、预留及库存动作接口。
- 真实 Shop 首期支持整单全额退款及多件订单按退回商品金额进行的部分退款。退款申请必须经人工审核；审核通过后由 Shop 服务端按订单行、退回数量和已退款余额计算可退金额，再调用已验证的支付服务商接口，记录请求、结果与失败待办。任何累计退款不得超过原实收金额，重复审核或回调不得重复退款。AI 客服只能发起申请，不能执行退款；Inventory 不处理资金。
- 审核通过的全额或部分退款必须优先退回顾客原付款方式；Acuven 须在人工审核通过后 24 小时内发起原路退款，周末和节假日照常计时，实际到账时间按支付服务商及银行处理进度展示，不承诺即时到账。服务商对卡、FPX 和实际上线的钱包的退款能力须在正式开户后逐项核验。若服务商确认无法原路退款，不得假报已退款；由人工联系顾客核实身份与银行资料，取得顾客对银行转账的确认后再执行，并记录核验、确认、付款结果和失败待办。AI 客服不得收集银行资料或独自执行该例外流程。
- 真实 Shop 首批商品名称、图片、描述和规格以 Acuven 现有 Shopee 商品资料为基础，导入后由 Acuven 人员人工核对；售价、运费等仍在 Shop 单独设置。若 Shopee 开发者权限未获批，从卖家后台导出资料，或整理商品表格和图片，再人工导入核对，不等待商品 API。
- 真实 Shop 首批销售类别为 3C 电子配件，其中包含内置电池的商品，但首批没有单独电池或移动电源。导入商品时逐项核对实际品类、品牌或兼容性表述、包装内容、颜色/尺寸等规格及售后条件；网站展示的商品类别须与支付商户资料中的实际业务相符。用户确认当前国内人工寄件方式可寄送这类内置电池商品，并了解申报与包装要求；开放真实结账前仍按具体商品和配送路线核对承运条件，不能因一般电子配件可寄送就默认所有带电池型号都可寄送。[EasyParcel 的电池寄件说明](https://helpcentre-my.easyparcel.com/support/solutions/articles/9000223923-how-to-declare-parcel-content-that-contain-liquids-and-batteries-)提示应准确描述安装在设备中的电池并核对所选承运商限制。
- 首批真实 Shop 接受西马、沙巴和砂拉越的订单，服务端按收件邮编、商品与可寄送路线决定是否允许结账；配送费按收件地区及商品重量计算，结账前显示该订单的应付运费及预计配送时间。部分首批商品已有含包装重量与尺寸资料，其余须在开放结账前逐项称重测量并核对。若人工寄件的实际承运收费高于顾客结账时已支付运费，差额由 Acuven 承担，不向顾客补收；若实际收费较低，仍按结账时显示的运费收取，运营定期根据差异调整报价表。已付款且库存可用的订单须在付款确认后 48 小时内交给承运商，周末和节假日照常计时；用户已确认现有人工寄件方式在这些日期也可办理。新加坡首期不开放。用户确认现有人工寄件方式明确覆盖这三个地区的内置电池商品；上线时仍须核对实际商品、申报、包装、运费和邮编配置。
- 首批 3C 配件包含蓝牙、Wi‑Fi 或其他无线功能商品。用户确认每个首批无线型号均已备有可核对的马来西亚 SIRIM／MCMC 认证或标签资料；上架前仍须按具体型号核对适用认证与标签、有效期及供应来源，并保存审查结果，不能把“资料已备”当作“已验收”。[SIRIM QAS 的通信、媒体及混合设备认证说明](https://www.sirim-qas.com.my/service/communication-multimedia-and-hybrid-product/)用于制定核对清单，实际适用范围以型号与主管机构要求为准。
- 首批商品仅以自有品牌或无品牌销售；用户确认商品标题、图片和包装不使用第三方公司商标。导入 Shopee 资料时仍需逐项核对品牌字段与图片，不沿用与真实商品不符的标识。
- 真实 Shop 允许访客直接下单；顾客通过 AI 客服查询、修改或取消本人订单，以及申请退款时，必须先登录并完成聊天会话绑定。访客订单可在顾客登录后，通过发送至订单手机号的一次性短信验证码验证并认领、绑定账号；未认领前 AI 客服不得以聊天资料推断订单归属。
- 用于真实站会员登录和访客订单认领的生产短信验证码账号尚未开通；开户、真实发送验证和限流配置是相关功能的上线依赖。
- 若真实 Shop 使用当前 Acuven Technology Stripe 账户，Shop 每笔付款、退款及回调必须绑定 Shop 自己的订单和付款记录；开发服务费与 Shop 商品款在报表和对账中可区分。Shop 退款后台只能对已归属本店订单的交易发起操作，不得让开发服务的收款或退款事件改变 Shop 订单。共用账户的顾客可见名称、网站和业务资料需经服务商核实。
- 若真实站上线时短信验证码尚未可用，可先允许访客下单；会员订单认领及 AI 客服订单操作保持关闭，直至短信真实送达和登录绑定链路通过验收。此期间不提供访客在线自助取消/退款申请，但在订单确认页和通知中提供与 AI 客服共用的 WhatsApp 入口；AI 识别售后请求后转人工。人工客服先回拨订单原填写手机号核实申请人；若多次回拨无人接听，由 Acuven 管理员核对其他订单与付款证据后决定是否处理，不自动通过或拒绝。回拨、备用核验依据、决定、处理人和时间在 Shop 售后记录留痕；完成核验前不向 WhatsApp 请求者透露订单资料或执行取消/退款。AI 和 Inventory 不接收付款证据。
- 顾客通过真实店 WhatsApp 入口提出取消或退款请求后，人工客服须在请求进入人工队列后 24 小时内首次回应；用户已决定每天都计为工作日，包括周末和节假日。记录入队与首次人工回复时间；首次回应不代表已经审核通过或完成退款。
- 真实 Shop 的隐私告知、配送说明、取消/退货退款规则和服务条款目前均无正式版本，须从头准备、由经营者核对实际执行流程后发布。正式接单前，公开页面需清楚显示经营主体与客服入口、商品说明、配送和售后规则，并在结账前可访问；[Stripe 网站审核说明](https://support.stripe.com/questions/business-website-for-account-activation-faq?locale=en-GB)也要求商户网站展示与账户资料一致的业务和售后信息。面向马来西亚顾客的隐私告知按[马来西亚个人资料保护部门指引](https://www.pdp.gov.my/ppdpv1/wp-content/uploads/2025/01/A-Quick-Guide-to-PRIVACY-NOTICE.pdf)准备马来语与英语版本。具体承诺、地址、联系方式及适用法律文字由经营者核实后再上线，不能直接复制 Demo 文案。
- 除商品故障、错发等另须处理的情形外，真实 Shop 自愿接受顾客因改变主意，在收货后 7 天内申请退货；收货日以承运商显示的签收日期为准，有争议时人工核实。申请获准后须在 7 天内寄出退货，按寄件凭证或承运商首次揽收时间判断。退货送达 Acuven 后，人工须在 48 小时内完成验收并告知顾客审核结果，周末和节假日照常计时；验收确认商品未使用、配件齐全、无损坏，允许顾客拆包作合理检查。此类退回寄件费用由顾客承担，原订单已付配送费不退，只退实际退回商品的价款。政策页面须说明申请入口、状态确认、退回地址、验收条件、退款触发条件和预计处理时间；多件订单只退部分商品时按已审核的退回订单行做部分退款，不能误退其他未退商品。整单优惠按各商品原价占比分摊，部分退款以退回商品实际支付金额为上限。例如两件商品原价分别为 MYR 60 和 MYR 40，整单优惠 MYR 10；只退第一件时，其分摊优惠 MYR 6，可退商品价款 MYR 54，原配送费另按上述规则不退。商品故障或错发的运费另按适用规则处理。
- 真实店铺首期使用 `ai_chatbot_demo` 已有的 Demo WhatsApp 号码，AI 与人工共用该入口。新对话默认进入真实店客服；Demo 访客通过专用演示链接或菜单进入。真实顾客与多行业演示访客的会话、工具权限和数据必须隔离，切换模式不得带入另一模式的历史资料或权限。
- 真实站支付成功与否由 Shop 的服务端核验，向 Inventory 发送最小库存事件；Demo 站不得调用真实库存写入或真实支付服务。旧演示订单不能导入真实订单账。
- Shop 项目须另行更新需求、交易设计、页面提示、测试与部署计划，明确马新配送及真实退款等规则；这些改动不由 Inventory 仓库越界完成。

### 4.6 AI 客服改造

**独立运行要求**：Inventory 与 AI 客服解耦。库存后台、规则、API、数据库和作业可独立运行，不依赖 Chatbot 代码、LLM key、WhatsApp 或对话流程；关闭/替换 AI 不影响正常库存生命周期。AI 只作为受限 API 调用方，订单与售后仍调用 Shop。具体边界与故障验收见[独立运行和 CRM/ERP 集成设计](SYSTEM_DECOUPLING.md)。

`ai_chatbot_demo` 目前零售 bot 使用 ERP 查库存和创建订单。接入后，该 bot 的库存查询改用 Inventory；顾客登录、订单、支付、物流、改单与退款申请仍调用真实 Shop 的受限 API。其他行业演示的 ERP 功能不自动切换。

- 客服只通过受限业务 API 查 Inventory 库存与 Shop 本人订单；顾客必须先通过真实独立站登录，客服再取得有期限且限定该顾客的授权。WhatsApp 号码或自报订单号不等同于登录。首批自助改单只覆盖真实 Acuven Shop 订单；Shopee/TikTok Shop 订单走各自平台的买家身份与售后流程。
- 代下单前展示商品、规格、数量、含运费应付金额和地址并获得顾客明确确认；真正提交采用幂等键。在线支付由服务端生成支付链接或安全结账入口，客服不接触卡资料。
- 订单未发货且顾客已登录时，可通过服务端再次校验后修改地址或取消订单；提交前再次检查最新履约状态。若已创建运单但尚未交运，须先确认能作废或更新运单，不能只改订单地址。已发货或平台不允许操作时交人工处理。退款申请只能建立待审核请求，由人工决定，AI 不能直接触发退款。失败、超时或结果未知时交人工核实。
- 不向 AI 模型提供其他商户、其他顾客或不必要的个人资料。工具调用有可追溯审计。

**模式隔离验收**：同一 WhatsApp 号码不等于共享业务授权。真实零售客服建议使用独立服务部署和工具白名单，行业 Demo 保持独立；Demo 导演台全局工具开关不能关闭真实客服工具，演示会话不能访问真实库存数量、订单或写接口。切换模式须清除/隔离上下文并撤销原聊天订单授权；网关路由及人工台明确当前模式，详见 [DELIVERY_PLAN](DELIVERY_PLAN.md)第 5 节。

### 4.7 其他网店与平台的扩展要求

后续独立网店的具体类型尚未选定；首期交付通用库存协议及 Acuven Shop 接入，后续网店连接器按实际选型再开发。

本阶段把接入方便性、规范性、安全性列为设计目标；具体规则见[接入规范](INTEGRATION_STANDARD.md)和[接入指南](INTEGRATION_GUIDE.md)。自建网店使用 reserve_api，无法控制结账的平台用 platform_adapter，未完整接通的渠道用 manual_quota；这三种模式不相互冒充。

- Acuven Shop 是首个自建网店连接，库存对接采用可复用的服务端 API 与库存事件协议，库存核心不能依赖 Acuven Shop 的数据库结构或代码。网店商品规格 ID 映射到中心 SKU；每个网店连接有独立的连接标识、服务凭据、权限、配额和同步状态。
- 其他自建网店可实现同一版本的库存查询、预留、确认销售、取消释放、出库及实际退货入库协议。已有商业网店系统或购物平台通过各自适配器转换接口和事件，复用中心 SKU、库存流水与配额规则；新增平台需要单独取得权限、核对事件含义、验证接口限制并验收。
- 对接先服务同一 Acuven 经营主体的多个网店／店铺。将来为其他商户独立部署时使用各自实例和凭据；若发展为 SaaS，须先完成并验证租户隔离和商户授权，才能让不同商户共享部署，不能仅增加店铺记录就视作多商户隔离已完成。
- 管理员主动停用或迁移网店连接时，先停止该连接的新订单库存接入，保留存量订单所需的确认、发货、取消和实际退货动作；存量占用不能因停用而直接清空。核对存量预留、未发货占用与售后记录后，管理员再确认最终关闭。此流程须由网店同步关闭新订单结账或完成经核对的库存交接，避免两个系统同时分配同一实物库存；凭据已撤销或授权失效时仍按拒绝调用与人工核对流程处理。

**验收**：Acuven Shop 只通过协议访问库存，不直接读写库存数据库；不同连接的外部商品或订单行编号相同也不会混淆；一个连接的凭据不能操作另一连接的预留或库存事件；模拟新增网店可经同一协议完成库存动作，无需修改库存核心计算逻辑。该扩展验收不代表任何后续第三方平台已完成真实接入。

**接入体验与安全验收**：管理员按“类型 → 凭据/官方授权 → 规格映射 → 只读检查 → 期初与份额核对 → 启用”完成配置，测试连接不写真实库存。接入方能读取自己连接的能力、实际限额及已确认映射，获得同版本 OpenAPI、示例和故障流程；缺权限不声称完整自动同步。服务凭据分连接/环境并按动作授权，可轮换撤销；顾客/AI 状态身份不能取得数量或写权限，网店服务不能改现货/配额/映射。外部店铺复用适配器仍须独立授权和核对，未知网店不承诺仅填网址即自动接通。

后续网店的库存故障销售政策要逐连接声明和评审，不自动继承 Acuven Shop 的持续收款选择。平台 API 版本、库存语义、官方权限及真实能力单独核实；首期不用 SaaS、多语言 SDK 或任意插件执行作为方便接入的前提。

### 4.8 后续 CRM 与 ERP 集成

系统群计划让 CRM、ERP 进入 Acuven 真实经营，以现有 crm_os、erp_os 为候选改造底座，具体接口、租户和迁移设计尚未冻结；客户外部系统按选型/合同另接。CRM 的客户档案、线索/服务记录与 ERP 的采购、供应商、成本/财务分别在所属系统处理；Inventory 仅接必要库存查询和事实，不复制顾客/财务资料。

业务系统集成身份与销售店铺连接分开：CRM/ERP 不自动占渠道配额，不借网店凭据取得全局写权限。后续企业业务 API 单独设计，不把供应商到货等新业务塞入当前顾客销售/退货事件。

最新系统群决定将数量实现落在唯一共用基础账：自家 ERP、Shop、POS 与 Inventory 经 Core 写入已核实事实，Inventory 对多入口协调份额与平台同步，不拥有另一私人实物账。ERP 保留采购/成本/经营单据，读取同账结果，不重复扣减。Core/所属集成保存异步出站和补交；ERP 暂不可用不阻塞已验收的库存事务。Acuven 经营单据按日/渠道汇总，逐笔原始交易留原渠道，Inventory 不新增金额或发票字段。独立部署、映射、权限、故障及初始迁移要求见[补充设计](SYSTEM_DECOUPLING.md)，现行数量归属见[共享核心决定](decisions/SHARED_COMMERCE_CORE.md)，旧[库存方向](decisions/ERP_INVENTORY_AUTHORITY.md)保留历史。CRM/ERP 实际连接器不加入首期上线条件。

## 5. 非功能与运营要求

- **一致性**：Core MySQL 事务保证唯一数量账、预留及配额；外部平台使用事件去重、出站队列与定期对账。跨平台“绝不超卖”无法仅靠异步 API 保证，必须显示延迟和异常。
- **可靠性**：平台 webhook 验签、去重、快速应答；按平台限流退避重试；定期补拉订单和库存，检测漏事件及长期差异。
- **库存历史保留**：入库、出库、手工数量调整、配额变更及影响库存的最小来源事件长期保留，并能按 SKU、连接及时间查询历史变化；更正以带原因的反向／纠正记录保留原始事实，不能直接覆盖历史。该业务记录保留要求独立于数据库备份的 30 天恢复窗口；不要求长期保存含敏感字段的原始接口报文。
- **灾难恢复**：真实 Inventory 的库存数量、预留、配额、映射、最小销售事件和审计流水发生数据库故障时，恢复点目标为故障前最多 15 分钟的数据损失（RPO ≤ 15 分钟），4 小时内恢复到可核对库存和处理新销售的状态（RTO ≤ 4 小时）。须保留至少 30 天的可恢复生产备份及所需连续变更记录，并通过隔离环境恢复演练验证；恢复后先核对 Shop 未补交库存事件、平台销售和人工配额差异，再恢复自动写库存。Demo 的定期重置不能覆盖生产备份。
- **安全**：传输加密、最小权限、商户数据隔离、凭据加密、轮换和撤销；生产凭据不进 Git、日志或 OpenClaw 工作区。用户决定首期真实后台管理员仅使用密码登录，不强制双重验证；生产管理员必须使用独立账号，不与共享 Demo 账号或其他人员共用。登录须限流、记录异常尝试并支持立即停用账号；所有库存数量、配额和店铺连接变更保留操作者与原因。双重验证列为后续安全增强，不得在现阶段文档或演示中声称已启用。
- **隐私**：Inventory 只留库存扣减所需的最少订单标识，不复制顾客姓名、电话、地址、支付资料或对话。Shop 和 AI 客服各自更新真实交易的数据处理说明。
- **可观测**：按商户、渠道和店铺显示最近同步时间、队列积压、授权状态、失败原因、差异件数和人工待办；同步失败、授权失效及可能超卖时，通过独立的库存运营 Telegram 机器人或群组主动通知 Acuven 管理员，并在后台显示告警。可能超卖等严重异常全天提醒，首期由 Acuven 负责人本人接收并决定是否暂停销售、核对及恢复同步；未确认的严重告警每 15 分钟重复，直到确认。当前没有备用负责人：严重告警发出 1 小时仍未确认时记录超时待办，继续只提醒本人，不自动通知其他人或停售。单纯 Shopee 人工核对逾期只在后台显示，不发 Telegram；若核对后确认数量冲突或可能超卖，则按严重异常提醒。已上线 Inventory 发生临时故障时，负责人须在收到严重告警后 1 小时内决定是否继续接单并留下决定记录；未作决定时记录超时，系统不会在这一时点自动停售。其他普通异常每天仅在马来西亚当地时间 09:00–18:00 主动提醒，周末和节假日相同；后台始终记录所有异常。该通道与 OpenClaw 开发任务通知分离；敏感字段不得进入普通日志。
- **性能与时效**：渠道实际 webhook、轮询、写库存频率和限流在获得应用权限后逐项实测，记录各渠道 P50/P95 同步延迟，再确定公开服务承诺。
- **财务边界**：Inventory 不计算价格、不处理或对账资金。真实 Shop 自己负责支付与退款；市场平台由平台自身处理。将来其他商户用各自账号。
- **语言**：首批库存管理后台和 Demo 的导航、库存状态、错误提示及关键操作说明支持英文与简体中文；SKU 和平台原始字段保持原样。

## 6. 分阶段交付与完成标准

业务目标：按系统群依赖分阶段交付可操作 Demo 和真实自用，不再设约一个月或固定上线日期。先完成现有 Shop Demo，再定/实现共用目录和基础账，开发 Inventory V1，随后真实 Shop 和获权平台；完整功能与质量优先。若 Shopee 与 TikTok Shop 的开发者权限届时均未获批，Demo 和真实独立站仍先上线，平台获批后再接入；不能将未获批接口当作已接通。若跨境物流仍未准备好，真实站仅向马来西亚开放结账，新加坡订单待可履约后启用。
上述真实站先上线以 Inventory 库存基础能力已通过验收、初始库存已核对、正式支付已可用为前提。若目标日期 Inventory 本身仍未准备好，Demo 先开放，真实站暂不接单；“Inventory 已上线后发生短暂故障时继续收款”只适用于此前已完成上线验收的真实站，不作为跳过首次验收的办法。
若届时 Shopee 接口仍未获批但店铺继续销售同一 SKU，真实 Shop 上线前还必须完成卖家后台固定配额、Inventory 人工渠道份额及每日不少于两次的人工对账排班与演练；未满足时，真实 Shop 只能先售卖 Shopee 未上架的 SKU。TikTok Shop 在尚未开始真实销售、接口也未就绪时不占用可售配额；开始销售前须先完成自动接入或人工配额验收。

| 阶段 | 交付与退出条件 |
| --- | --- |
| 0：开发者准入，**首要任务** | 优先为自营 Shopee、TikTok Shop 确认官方注册/申请路径和应用权限，提交申请并记录可追踪状态；核对未来多商户连接器要求。Lazada 申请列入后续，不作为首批上线闸门。 |
| A0：共用核心前置 | 目录稳定身份、租户/池及唯一基础账、数量/预留契约、语义迁移与恢复验证；建议 Core 项目尚未创建。 |
| A：Inventory V1 | 基于 Core 的单池试点、规格映射与库存视图、安全库存默认 2 件、固定渠道配额、Shop 原子预留、最小销售事件及异常面板；Shopee 接口未就绪时支持人工配额、人工销售事件登记与逾期对账告警。 |
| B：两套独立站 | Shop 仓库另行交付 Demo 与真实站两个隔离部署；真实站接 Inventory 库存并自行完成真实订单/支付/履约。 |
| C：已可用市场平台 | 自营 Shopee、TikTok Shop 哪个先获批就先完成规格映射、库存读写、最小销售事件、撤权与对账演练并上线。 |
| D：AI 客服 | Acuven 零售 bot 查 Inventory 库存，订单动作经真实 Shop 登录与 API；退款申请由人审核。 |
| E：产品后续 | 其他平台、Lazada、多仓/POS、组合装和可选业务扩展按契约验收；SaaS/专属/自托管已属目标，部署与租户隔离证据分阶段交付。 |

首批试运行的判定：Demo 与真实 Shop 的数据和支付严格隔离；真实 Shop 接入 Inventory 库存并可正常下单支付；已获批的自营市场平台逐一完成真实库存同步，未获批平台以明确“待开通/人工配额”状态保留；Shopee 未接通时，同一 SKU 的卖家后台份额与 Shop 份额不互借且人工核对可追溯；同一 SKU 的数量、固定配额和安全库存可核对，重复/漏事件及授权失效有明确处置。Lazada、多仓/POS 和 Inventory 订单/资金管理不属于自营 V1 完成条件；SaaS 是已选交付目标，外部多租户生产另经隔离验收。

对外展示的 Inventory Demo 使用独立部署/数据库中的模拟 Shopee、TikTok Shop 和独立站连接及示例库存事件，页面明确标注 Demo；不得连接 Acuven 真实店铺、复用生产令牌或展示真实库存与订单标识。
潜在顾客进入公开 Demo 前须登记邮箱或 WhatsApp 联系方式，真实线索通过独立流程进入 CRM，不因登记自动营销。随后使用共享示例体验账号；该账号只能访问模拟数据和演示环境，不能访问任何生产功能或凭据。顾客可以修改示例库存及安全库存；系统每周自动恢复初始示例状态，管理员也可手动重置。共享账号的改动对其他同时在线的顾客可见，页面应提示示例数据可能被重置。
Demo 的主要下一步是让潜在顾客预约与 Acuven 进行产品演示或洽谈。演示流程结束处提供清晰的按钮，跳转至**已可正常收发消息的独立商务预约 WhatsApp 号码**，并预填预约意图；该入口与真实店客服及 Demo 共用客服号码分开。共享演示账号不得读取预约对话或联系人资料。

## 7. 首期明确不做与待确认

首批 Inventory 不做多仓、组合装、完整订单后台、支付/退款执行、物流打单、商户自助注册、SaaS 计费、其他商户的 AI 客服与 Lazada 适配。真实 Shop 的交易与马新配送规则须由 Shop 项目另行设计，本文不代替它的支付或税务设计。

上线前仍需确定：自营店铺实际获批的 API 权限、每个 SKU 的期初盘点与人工配额表、两个独立站的部署与数据隔离、真实 Shop 最终选择 Stripe 还是 Billplz、正式退款和提现是否可用、Shop 会员和演示订单的处理边界，以及客服登录会话绑定方案。若选 Stripe，按已确认的方案复用当前 Acuven Technology 账户收开发费与 Shop 商品款；用户已确认两类业务由同一马来西亚经营主体承担，还需在 Stripe 官方后台使业务说明、网站和收款名称与实物商品销售相符，并完成证件、付款方式、退款和提现验收。Shopee/TikTok 开发者准入已启动；等待审核期间并行开发库存基础。

## 8. 文档完成度与验收追踪

业务范围足以进入具体设计评审，但仍不是已通过的生产交付。库存实现前评审新增状态规则和接口契约；跨仓库改造需在各自项目落实，不由一个库存任务越界修改。

| 要求 | 设计位置 | 必需证据 |
| --- | --- | --- |
| 实物/需求/份额一致，取消和退货不双加 | STOCK_RULES 第 1–6 节 | 数量例子复算、MySQL 并发、乱序/重复测试。 |
| 通用网店连接、整单预留及持久补交 | API_CONTRACT 第 1–7 节 | 双端 schema/身份隔离、超时恢复、缺货不进入付款。 |

| 真实/演示客服共用号码隔离 | DELIVERY_PLAN 第 5 节 | Demo 控制不影响真实服务，切换后旧授权无效。 |

## 9. 系统群组合、门户与核心要求

商品目录/基础账随 Shop、POS、ERP、Inventory 任一相关模块交付；同客户组合共用同一逻辑实例。Inventory 标准支持连接器只在获权、实现及验收后列为已支持。ERP 收货加一个销售入口无需 Inventory；两个销售入口共卖同一池须启用 Inventory，未购时不同实物池不得互借。单模块的基本记账和 POS 设备离线额度不被错误包装成必须买 Inventory。

原始身份保留稳定目录 ID，参考价不自动改变渠道成交价；池/地点引用、租户/权限和原子配额执行纳入核心契约。门户一次登录只在已购模块范围操作，各业务模块重验对象和角色；Inventory 保留独立入口，AI/门户失联不阻塞本地合法库存动作。SaaS、专属、自托管及限时客户授权支持分别验收。

POS 多仓/设备额度及现场生产仍属后续专项；Inventory V1 不以已有 ID 字段宣称已支持。公开 Demo 的登记线索在 CRM 隔离保存、重置不删除、只跟进主动咨询；库存示例不收真实顾客资料。

完整变更矩阵、Core/Inventory 事务技术闸门及组合验收见[架构对齐](HUB_ARCHITECTURE_ALIGNMENT.md)。Core 尚未创建，相关数量/身份实现不能直接采用旧私有账任务设计。
