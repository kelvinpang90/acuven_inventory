# 需求与交付流程复核

> 日期：2026-10-07 · 复核对象：0.7 草案。依据本地需求、开发、库存规则、API 契约、交付和运营文档。未重新查询官方审批状态；未修改已确认业务规则或其他项目代码。

## 1. 结论

产品边界、单地点库存、渠道配额、Shop 责任、Demo/真实隔离和未来通用接入方向已明确。可以推进建仓与基础任务设计；库存写入、真实交易和自动平台同步仍需关闭下列设计缺口。当前缺口集中在冲突处理和交付执行，增加功能范围不能解决这些问题。

优先级：P1 是相关状态/同步功能编码前要明确的规则；P2 是交付或真实上线前必须落实的流程。设计待批准与外部权限待获批分别跟踪，不能以文档已写替代实现验收。

## 2. 需要继续打磨的事项

### R01 / P1：库存发布旧任务不能覆盖新目标

依据：DEVELOPMENT 第 5 节已有目标版本、超时回读与销售核对；STOCK_RULES 第 5 节已有转移阶段。还缺旧任务废弃和未知写入阻塞后续写入的完整规则。

例子：旧任务准备向平台发布 5，之后销售使最新目标变成 3；旧请求重试或迟到，仍写 5，可能把已经售出的数量重新上架。仅增加本地版本号不能保证平台会拒绝旧请求。

建议设计：按连接 + SKU 串行发布，执行前校验目标版本，未发出的旧任务被新目标取代；结果未知时保留隔离并阻止后续增量发布，先核对平台与期间销售，再生成最新目标。平台不支持比较版本写入时，不宣称远端具有本地事务的保证。Q 与 T 在转移各阶段的归属必须同事务转换，不能既计入待增 Q 又计入 T。

关闭标准：旧任务迟到、减量未知、目标失败、并发平台销售都有数字例子和适配器能力闸门；CI 证明旧目标不会通过普通重试重新发布。此项在自动调配/平台发布编码前完成，库存基础可先开发。

### R02 / P1：取消、发货和库存释放的冲突

依据：REQUIREMENTS 第 4.3/4.6 节允许符合条件的取消，退款人工审核；STOCK_RULES 将取消释放与资金分开。还缺“提出申请”和“订单已取消”的明确边界。

例子：顾客申请取消，同时运营提交交运；若两边都成功，可能既释放库存又真实寄出商品。另一问题是申请尚未批准时是否已让库存重新销售。

建议：Shop 是决定是否已取消/已交运的唯一服务，使用订单版本或事务锁，只允许互斥结果；Hub 只在 Shop 确认取消后释放，不因聊天请求或退款申请到达就释放。打印面单、拣货、实际交运的边界分别定义。已确认取消后退款失败仍保留独立待办，不把已取消订单自动恢复成可发货。

经营者待确认：已付款未交运、身份及可取消条件核实后，是系统立即取消并释放，还是等待人工批准取消；退款仍单独人工审核。本轮已通过单问题弹窗询问，未以默认选项视为确认。

关闭标准：取消/交运竞争只产生一个合法结果，重试不重复释放；申请、确认取消、退款审核、资金退款各有状态及操作权限。

### R03 / P1：人工 Shopee 切换自动接入的事实去重

依据：REQUIREMENTS 第 4.1 节已有最后人工核对时间、补拉与去重；API_CONTRACT 有 event_ref 和订单行引用。但人工动作引用如何与官方事件、部分出库或补拉累计状态对应，尚未具体定义。

仅按官方 webhook ID 去重不能证明人工登记和后来的 webhook 是同一事实。时间窗口也不能代替数量去重，窗口边缘可能有迟到销售或取消。

建议：人工表单必须保存官方订单及订单行的稳定标识、动作数量和可用的动作引用；适配器建立官方事实到内部行计数的对照。初始已售未发货占用、人工登记和自动补拉共用行累计台账。没有可识别动作 ID 的累计数据，用权威累计状态和已处理数量算差异，不能每次当新增动作。

关闭标准：同一订单在人工、首次补拉、webhook 中重复出现，以及人工已录部分出库后自动补齐，余额仍与实物一致。接管记录明确时间、行计数和待核对清单。

### R04 / P1：SKU 映射变更的存量订单归属

依据：REQUIREMENTS 第 4.2 节保留历史 SKU；STOCK_RULES 规定订单行 SKU 不变。还需说明存在 active 预留、未出库需求或待处理事件时是否允许改当前映射。

例子：某规格原来映射 SKU-A，仍有未发货订单，管理员把当前映射改为 SKU-B。之后旧单出库若按新映射解释，会扣错 SKU。

建议：默认阻止有存量引用的规格直接换到另一实物 SKU；新事件优先匹配已登记订单行的原 SKU，而不是仅查当前映射。确需纠正历史错误时走管理员专门迁移/纠正方案，核对两侧数量及平台展示，不普通编辑覆盖。

关闭标准：映射变更前后旧单、新单、迟到取消和退货各扣/返正确 SKU；存量阻止条件及人工纠正有审计。

### R05 / P1：不可售数量与盘点纠正的约束

依据：STOCK_RULES 第 1 节要求 U ≤ O，第 2 节盘点目前只明确调整 O。

例子：账面 O=1、U=1，盘点发现实物为 0。仅将 O 改为 0 会违反 U ≤ O；拒绝实盘又会保留错误余额。

建议：盘点表单分别核对实物总数与不可售实物，管理员同事务纠正 O/U 并写各自差异流水，H/C 仍保留。实物不足产生需求缺口，不能靠清占用消掉。不可售退货后来检验可售时，也需定义明确的 U 减少动作和原因，不能再发一次退货入库使 O 重复增加。

关闭标准：实盘少于原不可售量、不可售转可售、并发出库都有可复算例子；纠正不覆盖有效销售需求。

### R06 / P2：把交付方向变成完整的可执行计划

依据：DELIVERY_PLAN 已列 001–016 候选任务，告警、Demo 重置、配额发布、备份等仍是待拆方向；其他仓库是改造包，尚未落实到各自契约。

建议：补一张完整任务依赖图及演示/真实上线必需项；优先实现可在隔离环境验证的整条小流程：SKU → 到货 → 配额 → Shop 预留 → 确认 → 出库 → 流水，而非直到全部后台完成才首次联调。自动调配保留需求，按平台能力单独启用；未获批的代码任务与申请事项分开。

每个 ready 任务要有精确共享文件、固定检查、必需 CI 名、设计文件和失败验收。OpenAPI 仍需生成机器可读版本；管理登录、库存操作及人工核对也要有端点契约，不能只有顾客结账 API。任务表中同时跨迁移/身份/API 或服务/作业层的条目，在登记时按模板拆小。

关闭标准：首批 1–3 个实际任务通过预审/contract_check；Shop、客服、网关各有独立任务与联调版本。指定建仓、复审、运营验收责任人，按实际任务估算四周目标，而非把日期当完成证明。

### R07 / P2：共享基础设施故障的恢复闭环

依据：OPERATIONS 有 Hub 备份、30 天恢复窗口和成功事件重放；Hub 与 Shop 共用现有服务器/数据库基础设施。

需要区分单库存库故障、共享 MySQL 故障及整台服务器故障。若 Shop 及其 outbox 也不可用，仅恢复 Hub 不能重建所有真实订单；“继续收款”也依赖 Shop 自己可持久保存订单。

建议：在 Shop 运维设计落实其订单、付款关联和已完成/待发送库存事实的备份；恢复演练覆盖两个服务恢复点不一致、故障中已付款回调以及平台继续销售。明确共享基础设施恢复负责人、远端存储和凭据恢复方式，库存恢复点不能直接当 Shop 资金状态的权威。

关闭标准：分别记录单库和共享故障的实际恢复耗时及差异；能找回订单、查询真实付款结果、补交库存而不重扣。已选 RPO/RTO 先按库存目标验收；Shop 的恢复目标另行明确，不擅自视为同样已批准。

### R08 / P2：统一异常状态与告警动作

依据：REQUIREMENTS 第 4.1 节明确人工核对逾期时停止增加该 SKU 在其他渠道的配额；DEVELOPMENT、OPERATIONS 的概览着重写仅后台提示/不停售，未完整重复这个增配限制。

建议：制定唯一的异常动作表，区分销售继续、Hub 新预留、自动增配、自动调配、向平台写库存和通知范围。单纯人工逾期不能被一处实现成全 SKU 严重异常、另一处仅 UI 红点；不自动停售也不等于所有写入继续。

另需明确 `unknown` 状态查询、服务 5xx、维护模式及 `needs_review` 的处理区别。后端可响应但无法核实库存时，应按明确错误语义处理，不能由 Shop 随意决定是否套用故障继续收款。

关闭标准：每种异常只有一套动作，测试覆盖普通/严重升级、告警确认不自动结案、平台不自动写 0、已知缺货不兜底收款。用户已确认的通知和持续销售选择保留。

### R09 / P2：真实 Shop 的商品与售后规则完成发布

依据：OPERATIONS 第 6 节已列地址变化运费、故障/错发与保修、优惠/积分、税费及支付方式例外。

还需把每项落实成可执行规则和页面内容：跨地区改地址是否补差/退差；故障/错发谁承担运费、采用换货还是退款、是否提供保修及期限；原付款方式不可退款的人工路径；结账及订单通知展示的真实承诺。库存服务不承担这些规则，但真实 Shop 上线必须完成。

经营者需要按问题逐个决定；纯技术的状态、幂等、队列和任务拆分可继续自主细化。正式政策发布及相关法律核验应在 Shop 项目完成，本报告不生成或认定法律结论。

1. 先确认 R02 的取消规则，随后在 Shop 状态机中细化；不改变退款人工审核。
2. 并行完善 R01/R03/R04/R05/R08 的技术方案和失败例子，再评审库存写入设计。
3. 把 R06 落为首批实际任务，先跑通隔离环境的库存生命周期；平台准入和支付认证同时跟踪。
4. 真实开放前完成 R07 恢复演练、R09 Shop 规则、支付/物流和初始盘点验收；Demo 可先独立交付。

本报告是后续优化清单，主文档仍为 0.7 待评审草案。关闭问题时同步主文档、接口、验收和任务依赖，记录已确认业务选择与技术方案批准状态，不仅修改一个段落。
