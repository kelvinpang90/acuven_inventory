# 库存数量与状态规则

> 版本：1.0 设计草案 · 日期：2026-10-07。补充 REQUIREMENTS 第 4.3–4.4 节和 DEVELOPMENT 第 4–5 节。以下为供评审的实现选择，尚未实施；涉及状态机和迁移的代码任务须通过设计闸门。

## 1. 数量口径

所有数量都是整数件。权威余额由 Core 按可信租户/库存池/地点/目录规格核算，V1 启用一个池/地点；订单行按 `connection_id + order_ref + line_ref` 核算。库存服务保留最小行引用和数量，不保存完整订单、顾客或付款对象。

| 符号 | 含义 |
| --- | --- |
| O / `on_hand` | 仍实际在地点内的全部实物，包含已售未发货与不可售物品。 |
| H / `held` | 未到期、未释放的待付款预留。 |
| C / `committed` | 已确认销售、尚未物理出库且未取消的需求数量；异常时也不能丢弃已确认销售事实。 |
| U / `unavailable` | 在库但不可售的数量，必须满足 `0 ≤ U ≤ O`。 |
| S / `safety_stock` | 安全库存，默认 2；非负配置值，可以大于现货。 |
| A / `available` | `max(0, O − H − C − U − S)`，表示全部渠道可分配的剩余上限，不代表每个渠道都能卖这么多。 |
| Qᵢ | 第 i 个连接隔离的剩余份额，包含已生效份额和待增加但已隔离的份额；不包含 H、C。 |
| T | 已从来源份额扣除、尚未完成目标分配的转移隔离量；不同时计入 Q。 |
| F / `unallocated` | 正常情况下 `A − ΣQᵢ − T`，尚未分配，不能直接由任一渠道使用。 |

本地 Shop 可预留上限是自身已生效份额，并同时受 A 和 SKU 状态限制。人工渠道及市场平台另保留 `confirmed_quantity`、`observed_at`、`target_quantity`、发布状态；这些是同步证据，不与 Q 再加一次。待增加份额虽已计入 Q，也不能视为已经在平台生效。

减量结果未知时，继续隔离来源原份额；不能先把拟减数量计入 T 或给目标增加。来源减量和期间销售已核对后，才把可转移数量从来源 Q 转至 T。平台可能有未上报销售，所以已确认读数不是永久有效的销售保证。

### 1.1 正常约束与异常状态

正常状态：O、H、C、U、S、Q、T 非负；`H + C + U ≤ O`；`ΣQᵢ + T ≤ A`；F 非负；余额等于不可变流水的累计结果。提高安全库存或实盘发现短缺可以打破销售容量约束，不能因此拒绝保存真实盘点或抹掉既有占用。

- `fulfillment_shortfall = max(0, H + C + U − O)`：当前预留及已确认需求超过可用实物的缺口。
- `allocation_excess = max(0, ΣQᵢ + T − A)`：安全库存等规则改变后，已隔离份额超过可分配上限的数量。
- 两项均为 0 仍可能有映射、平台展示、漏事件等差异；数值归零不自动恢复同步。
- 有上述缺口时，保留非负实物余额、既有 H/C 及原渠道证据，标记 `needs_review`，停止受影响 SKU 的新预留、自动增配和自动调配。A=0 不能隐藏缺口，也不能抹掉 Q 或销售需求。
- 已确认销售事实仍能入账；不可把真实已付款事件当作普通预留失败丢弃。C 可以因超卖高于实物，这是明确记录的需求缺口，不是负实物库存。
- 不自动向市场平台写 0，不自动停售任何渠道。Inventory 在线时的 `needs_review` 是明确业务结果，Shop 不得将其伪装成网络故障后继续收款；此前选择的继续收款仅适用于无法联系库存服务且无法核实结果的临时故障路径。

管理员修复映射、实物、销售占用和平台读数，并确认份额及待转移量符合约束、所有未知发布结果已核对后，记录处理依据才能恢复。告警“确认收到”不等于完成修复。

## 2. 状态变化表

每次数量变化由 Core 的唯一事务更新余额、行累计、预留/已生效额度执行记录、基础流水、幂等和变更 outbox。Inventory 政策目标和平台发布另保存；跨边界不得先减本地配额再远程占用数量，接口原子边界待 Core 设计验证。表中 q 为本次增量，不是累计数量。

| 动作 | 前置条件 | O/H/C/U 变化 | 份额处理 |
| --- | --- | --- | --- |
| 创建整单预留 | 全部行映射生效、SKU 正常、自身已生效 Q 及 A 足够 | H +q | 原连接 Q −q；整单原子成功。 |
| 有效预留确认销售 | 预留 active 且未到期、订单行完全匹配 | H −q，C +q | Q 不再减；整单将预留转 committed。 |
| 预留释放或到期 | active；锁内检查到期时间和最新状态 | H −q | 按第 3 节尝试恢复原连接份额，不能凭空增加其他连接配额。 |
| 无预留销售确认 | 已验证来源的真实销售事实；映射明确 | C +q，即使产生缺口也保留事实 | 原连接剩余 Q 减少 `min(Q,q)`；不足部分记录差异，Q 不变负。 |
| 未出库销售取消 | 已确认且尚未出库的部分 ≥q | C −q | 按第 3 节恢复原连接份额；与退款是否到账分开。 |
| 实际出库 | 未取消、未出库的已确认数量 ≥q，账面可出库实物足够 | O −q，C −q | 不再扣 Q；A 不因同一销售再减少。 |
| 可售退货验收入库 | 已实际收回并验收；未返库的已出库数量 ≥q | O +q | 新增 A 先进入 F，不自动恢复原店铺展示；管理员确认后分配。 |
| 不可售退货验收入库 | 同上，验收判定不可售 | O +q，U +q | A 不增加，不发布可售库存。 |
| 供应商到货入库 | 管理员、实际收到 q、稳定入库引用 | O +q | 仅此次 A 的正向增量可按已设置比例分配。 |
| 盘点差异纠正 | 时间口径对齐、管理员原因、余额版本一致 | O 增减差异量，不覆盖 H/C | 正差进入 F，负差触发约束校验；不自动重分配原份额。 |
| 改安全库存 | 管理员、非负整数、配置版本一致 | 仅 S 改变 | 不改变实物流水；增加 S 产生超额时进入核对，降低 S 的增量先进入 F。 |

未知映射的外部事实先持久接收为 `needs_review`，不猜 SKU。人工确认映射后在原事件上处理，不能另造一笔销售。物理出库事实与账面数量不符时保留待核对事实，先纠正账面/补齐前序，再应用原出库事件；禁止强扣 O 为负。

首期没有损坏出库专门流程；不可售退货仍要纳入实物台账。表中的部分取消/出库/退货数量是库存协议的累计约束，不代表 Shop 首期承诺拆单发货界面。

## 3. 释放数量回到哪里

技术方案采用“优先原连接，不满足条件则未分配”：

1. 释放 H 或 C 后重新计算 A。最多恢复本次释放量且不得使 `ΣQ + T > A`。
2. 连接仍 active、映射生效、无待核对差异时，可给原连接恢复份额；Shop 本地份额可事务生效。
3. 市场平台取消时可能自行回补展示量：适配器先核对销售及平台读数，只写绝对目标，不能再次向平台叠加 q。人工渠道生成确认待办。
4. 连接 draining/closed、SKU 异常、恢复容量不足的部分进入 F；异常时展示原待处理量与缺口，不将负 F 当作“剩余库存”。恢复正常前不自动外发。
5. 退货、盘点正差、安全库存降低产生的增量一律先进入 F；按比例自动分配只在供应商到货流程触发。管理员可明确分配 F，另留审计。

这项选择避免取消后无依据地迁移份额；补货仍按用户已确定的比例分配。接入其他网店时沿用同一语义。

## 4. 订单行累计量和重复处理

按连接、订单、行及不可变 SKU 保存 `confirmed_qty`、`cancelled_qty`、`dispatched_qty`、`returned_sellable_qty`、`returned_unavailable_qty`。

```text
outstanding_qty = confirmed_qty − cancelled_qty − dispatched_qty ≥ 0
returned_sellable_qty + returned_unavailable_qty ≤ dispatched_qty
C = 所有行 outstanding_qty 合计
H = 所有有效预留行数量合计
```

事件数量都是增量。每次发货、取消或退货必须有稳定独立动作引用，重试复用该引用；同一行多个合法动作不能仅以行 ID 去重。按 `connection + event_ref` 防重复事实，按幂等键防重复请求；另用累计上限防止来源换事件 ID 重复出库/取消/返库。若来源既换引用又伪造新退货事实，Inventory 无法自行辨认实物；Shop/平台适配器须提供可靠的动作引用及实物验收依据。

人工登记错误只能走管理员纠正流程：引用原事件和受影响行、保存核对依据及前后数量，追加补偿流水，不删除原事件或重写历史 SKU。没有后续依赖动作时，在同一事务撤销原错误的数量影响并重新校验份额；已有出库/退货等依赖时拒绝简单反向，进入整条数量链核对后形成专门纠正方案。纠正不能伪装成顾客取消或实际退货，网店服务身份无管理员纠正权限。

取消/出库先于确认销售到达时，事件保持待核对，补拉前序或最终状态，再按明确的数量链处理；不因到达顺序增减库存。事件批次处理失败整批不应用余额，不留下部分动作；事件接收本身仍持久保留。

预留到期判断使用数据库 UTC 时间和余额锁：`now ≥ expires_at` 即到期；付款通知里自报早于到期的时间不能自动复活过期预留。支付事实迟到采用无有效预留流程，保存需求和差异，再由人工处理。整个 active 预留一次转销售，首期不提供部分支付预留转换。

## 5. 整数比例和配额转移

比例使用整数基点，10000=100%；有效比例总和必须为 10000，未开始销售的渠道为 0。新增 n 件先计算各渠道 `floor(n × ratio / 10000)`，剩余件数按余数降序分配；余数相同按稳定 `connection_id` 升序，每次使用并保存同一比例版本。无有效比例或异常时 n 件进入 F。

调配只对符合条件的自动连接进行，按参与连接正比例重新归一化后使用同一尾差规则，人工及其他连接的 Q 不加入池。阶段为 `planned → reducing → source_verified → increasing → completed`，任何阶段可进入 `needs_review`。写入结果未知不推进阶段；目标失败保留 T 和已确认来源减量，再重试目标。放弃转移需要管理员核对后把 T 归 F，不能自动向来源平台补回。

## 6. 可复算验收例子

| 场景 | 初值与动作 | 期望结果 |
| --- | --- | --- |
| 正常购买 | O=10，S=2，Q(Shop/Shopee)=4/4；Shop 预留 2、付款、发货 | 预留后 H=2，Q=2/4，A=6；付款后 H=0/C=2/A=6；发货后 O=8/C=0/A=6。 |
| 预留到期 | 上例预留 2 后到期，连接正常 | H=0，A=8，Q 恢复 4/4；重复过期任务无新流水。 |
| 真实超卖事实 | O=1，S=0，C=0，Shop Q=1；故障期间收到已付款销售 2 | O=1，C=2，A=0，Q=0，缺口=1，事实已应用但事件 `needs_review`，不能声称库存确认。 |
| 安全库存提高 | O=10，C=2，S=0，ΣQ=8；S 改 2 | A=6，超额=2；保留占用及渠道证据，拒绝新增 Shop 预留，告警不自动停售。 |
| 部分退货 | 已确认并发出 3；退回可售 1、不可售 1 | O 增 2，U 增 1，C 不变；A 增 1 入 F；再重复其中一个事件不增加实物。 |
| 乱序出库 | 出库先到，确认销售后到 | 第一次出库未应用；补齐销售后应用一次，事件历史可查。 |
| 补货尾差 | 新增 3；两渠道比例各 50% | 稳定 ID 在前得 2，另一得 1；同入库重试不再次分配。 |
| 未知来源减量 | 来源 Q=6，拟转 3，平台请求超时 | 来源仍隔离 6，T=0，目标不增加；确认来源及销售后才改变。 |

测试使用纯领域数据和脱敏夹具；并发与 MySQL 事务需在 CI 的真实 MySQL 临时实例验证，不以 SQLite 锁行为证明生产并发安全。

## 7. 共用核心下的适用范围

本稿数量转换仍作为自营 Inventory 业务验收，数据所有者改为目录/基础账 Core。SKU 身份由目录提供；O/H/C/U、预留与基础流水在唯一账，S 与渠道份额是 Inventory 政策及账内已生效约束，不是另一本可修改余额。Q/T 原子执行方案未批准前不可独立编码两套状态。

每个约束和锁/幂等作用域含 tenant/pool/location/sku，不能凭相同 SKU 共池；未购买 Inventory 的单销售入口通过同一 Core 基础 API 记账，多入口同池需已验证模块授权。POS 设备离线额度和多仓不属于当前已交付能力。详见[系统群对齐](HUB_ARCHITECTURE_ALIGNMENT.md)。
