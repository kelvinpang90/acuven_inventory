### 2.1 为什么采用 API 加事件

- **同步 API**用于真实 Shop 正常结账时的库存检查、原子预留与释放，以及客服库存查询。Inventory 不可用时采用用户已选定的继续收款例外流程，未预留订单由 Shop 持久保存并等待人工核对。
- **webhook / 事件**只抽取影响库存的动作；Inventory 保存平台、店铺、外部事件/行 ID、SKU、数量与动作，不复制顾客或资金资料。接收后先持久化，再异步处理。
- **定期对账**弥补 webhook 丢失、平台延迟、商户在平台后台直接操作，以及本地写入失败。Redis 可做传递/短时锁；数量事实/幂等以 Core 持久账为准，Inventory inbox、发布作业和核对进度以本项目持久存储为准。
- 不共享数据库表，不让 Shop 或客服直接写 Inventory 的库存。跨服务操作采用关联 ID、幂等键与补偿流程。

### 2.2 数据负责方

| 数据 | 权威写入方 | 其他系统做什么 |
| --- | --- | --- |
| 实物库存、预留、基础流水 | Core 唯一基础账 | Shop 和客服只查或通过命令申请预留；渠道写入由适配器执行。 |
| 真实 Shop 商品页面、价格、促销、运费、税费、会员 | 真实 Shop | Inventory 仅保存 SKU 映射和库存数量，不保存金额快照。 |
| 真实 Shop 订单、付款、退款、物流、售后 | 真实 Shop 及其支付/物流服务商 | Inventory 仅消费影响库存的状态事件。 |
| 市场平台原始订单、活动和付款状态 | 对应市场平台 | Inventory 仅提取库存动作，不代替平台订单或资金后台。 |
| Demo 数据和模拟付款 | Demo Shop | 与真实 Shop 和 Inventory 完全隔离。 |

### 2.3 以 Acuven Shop 为首个连接的扩展协议

后续网店类型尚未确定。首期完成通用协议与 Acuven Shop 的接入，不预先交付未选定网店系统的专用连接器；后续选定系统后再核对官方接口及开发适配器。

共用 Core 提供基础目录/数量契约，Inventory 提供多入口版本化包装 API 与平台事件转换。Acuven Shop 后端是首个调用方，接口命名、鉴权和数据结构使用通用的渠道连接概念，不能将其数据库表、代码或固定店铺名称写入库存领域逻辑。首期仍只交付已确定的自营渠道。

每个网店／店铺使用独立 `connection_id`；连接记录包含渠道类型、归属、环境、能力状态与凭据引用。可售查询和预留返回该连接被分配的可售数量，不返回其他连接可用份额。服务端从已验证的服务身份确定可操作连接，不信任调用方任意指定的店铺；预留与库存事件必须绑定连接、中心 SKU、稳定的外部订单行引用和幂等标识。去重键包含连接标识，防止不同网店恰好使用相同订单编号时串账。

其他自建网店实现同一查询／预留／库存动作契约；商业网店系统及 Shopee、TikTok Shop、后续 Lazada 由独立适配器负责授权、规格映射、平台事件转换、库存读写、限流和对账。适配器只将经过核验的库存动作送入领域层，不修改库存计算公式。渠道配额与补货比例按连接存储，不能在数据结构中写死只能有三个渠道。接口版本升级须保持已接入网店的兼容性，或完成明确迁移后再切换。

Shop 在本地事务中保存订单状态与待发送库存事件，由持久化队列重试并查询结果；Inventory 去重处理并保存动作结果。同步查询与预留、异步库存事件及周期对账共同完成接入，不能以一次 HTTP 请求成功替代整个销售生命周期核对。Demo 和生产使用不同的连接与凭据，拒绝跨环境调用。

客户独立部署可复用协议和适配器；未来 SaaS 须另行实施并验证租户数据库访问边界、连接归属、授权和事件路由隔离。当前的多连接设计仅支持同一 Acuven 经营主体的多店铺扩展，不构成已完成的多租户功能。

管理员主动停用网店连接采用“正常接入 → 存量处理 → 已关闭”的生命周期。进入存量处理状态后拒绝新订单预留，但在凭据仍有效的前提下，允许与该连接切换前已登记订单／预留引用匹配的付款确认、取消、出库及实物退货事件；不能借存量接口创建任意新的库存占用。Shop 同步关闭新订单接入或完成明确的库存交接，旧预留仍遵守到期时间，既有占用保留并对账。管理员确认存量记录及售后交接完成后关闭连接并撤销凭据，不自动抹去历史流水。该主动迁移机制不允许授权失效或凭据已撤销的调用继续执行。

### 2.4 接入规范与接入包

新增连接采用[INTEGRATION_STANDARD](INTEGRATION_STANDARD.md)规定的 reserve_api / platform_adapter / manual_quota 三种 profile。生命周期补齐 draft/testing 的验证阶段；能力、授权、SKU 异常独立判断。网店接入用自己的连接凭据读取 metadata 和 confirmed mappings，不用后台管理员密钥，不通过数据库或名称猜映射。

首期提供[机器可读 OpenAPI 草案](contracts/inventory-v1.openapi.json)、示例和[调用指南](INTEGRATION_GUIDE.md)；之后以同契约校验 Inventory/Shop 实现和模拟连接。协议便利性由统一语义与接入包保证，已选购物平台差异封装到适配器，不要求库存核心针对每个平台改公式。

服务权限按事件动作拆分，Bearer scopes 由应用检查，所有 ID 都验证当前连接对象归属。凭据轮换、官方 webhook 验签、刷新互斥、请求预算及旧库存发布任务处理见接入规范；不能用 OpenAPI 格式通过代替这些行为测试。真实平台所需权限及接口版本仍以获批后台实测为准。

### 2.5 AI 解耦与未来 CRM/ERP

Inventory 是可独立启动、部署和运行的服务，AI 客服是受限客户端；库存代码不导入客服业务模块，环境不需要 LLM/WhatsApp 凭据，事务不等待 AI 决策。单独关闭客服须通过库存生命周期验收。

客户外部 CRM/ERP 通过 business integration 身份/适配器接入；Acuven 自家 ERP 经共用目录与基础账，区别于有 Q 配额的销售连接；实际 API 尚未设计/实现，不扩充当前网店 v1 OpenAPI 为已支持企业业务。客户与财务数据在目标系统管理；销售副本、实际到货、出库来源及去重有明确责任。

详见[SYSTEM_DECOUPLING](SYSTEM_DECOUPLING.md)及[共享核心决定](decisions/SHARED_COMMERCE_CORE.md)。数量权威是同一 Core 基础账，Inventory 接平台事实并协调份额，Acuven ERP 的收货/自身业务经 Core 记一次，账结果异步提供。ERP 日渠道经营汇总是独立业务流，不重新扣量；客户外部 ERP 另设适配器。Core/迁移及接口未实施，当前网店 v1 不声称已经支持 ERP。

## 4. 数据所有权与核心引用

基础账和目录的数据不在 Inventory 私有业务库权威写入。各仓库通过版本化 API/组件边界访问，实际库表/进程设计待 Core 评审；不授权跨库直写。

| 所有者 | 数据/聚合 | 约束 |
| --- | --- | --- |
| 目录 Core | 商品/规格 ID、SKU、条码、基本名称、参考售价、目录版本/审计 | 同租户逻辑身份一份；Inventory 的 sku_id 是目录规格 ID。 |
| 基础账 Core | tenant/pool/location/sku 余额、H/C/U、预留、最小库存事实/行累计、流水、数量幂等和 outbox | 同池一份权威账；单模块与组合都用同一种核心，不重复建账。 |
| Inventory | channel_connections、channel_listings/sku_mappings、Core 实例/池引用 | 所有引用绑定可信租户/池，官方规格到目录 ID 的映射不拥有目录身份。 |
| Inventory 政策，Core 原子执行 | 安全库存、比例、渠道目标、份额/转移政策版本、账内已生效额度及执行计数 | 本地目标不是可售确认；额度与 H/C 原子约束的 Core 契约冻结后才编码。 |
| Inventory | 平台令牌/能力、发布 outbox、补拉游标、差异、审计、服务凭据 | 不把平台密钥放 Core；tenant/连接/对象/动作多层权限。 |
| ERP/原交易系统 | 收货/成本/经营单据、订单/支付/退款/成交快照 | 原系统确认事实，经唯一账处理；ERP 日渠道汇总不再扣库存。 |

数量公式、默认安全库存 2、30 分钟预留、补货比例与长期基础流水的业务语义见 STOCK_RULES；它们是 V1 自营 Inventory 配置，不默认改变单卖 ERP/POS/Shop 的套餐规则。存量映射保留原目录规格 ID。

按 tenant + pool + location + sku 定数量范围；两租户同 SKU 代码、同租户分开池都不得共享额度。V1 只激活默认一个池/地点，多仓/POS 需后续设计。旧 ERP 的 reserved/quality_hold/incoming/in_transit/成本不能直接等同本稿 H/C/U，Core 抽离前做语义对照和迁移验收。

### 4.1 事务与例子

首期不配置按剩余件数触发的低库存提醒阈值，不自动将 SKU 切为单渠道销售；管理员自行判断并操作配额。该决定不关闭默认安全库存扣除、配额约束和可能超卖告警，也不应阻止正常补货按有效比例分配新增可售量。

新 SKU 的补货与自动调配比例由管理员逐项设置，不默认填入 Shopee／Shop 的比例。未配置、合计不为 100% 或无正比例渠道时不执行自动分配，新增可分配量保留为未分配库存；不能因为系统存在三个首期渠道就自动平均分配。尚未开始销售的渠道比例为 0。保存比例配置的版本与审计，补货及调配记录引用实际使用版本；单纯保存比例不立即改写旧渠道配额，后续新增分配或配额用完触发调配时再按规则使用。

已接通渠道配额用完时允许自动调配，但须作为独立且可重试的转移流程，不能先给目标增配再异步减少来源。转移记录保存 SKU、来源／目标连接、数量、版本、前置核对结果和每步平台确认；待转移份额须隔离，不能在两边重复分配。仅对适配器已验证支持可靠减量确认与销售核对、授权有效、映射明确且无未处理数量冲突的连接启用；按 SKU 串行核对转移及并发销售，不转移 `held` 或 `committed`。来源减量须得到平台确认并核对期间相关销售；超时或确认能力不足时保持待核对，不增加目标，也不凭猜测回滚来源展示量。目标写入失败保留减量事实与待处理份额，重试不得重新从来源重复扣量。数量策略为按该 SKU 已设置的渠道比例重新分配参与连接的剩余可调配库存；仅以这些连接现有未售、未预留的份额构成调配池，人工及其他非参与连接的份额不得混入。按参与连接的有效比例相对归一化并用整数件数处理尾差，比例为 0 的连接不增配，无有效比例或调配无法满足前置核对条件时生成管理员待办。盘点安全库存、占用及未完成转移后再计算，不凭比例凭空增加份额。例如两个参与渠道比例各 50%、共有可调配库存 6 件，一个剩 0 件、另一剩 6 件，则目标各 3 件，来源先减 3 件并核对成功，目标再加 3 件。人工模式连接不参与。该流程不宣称跨平台写入具有单事务原子性，适配器无法满足条件时回退管理员待办。

上线后每周完整实物盘点，出现异常即时核对。盘点期间继续入库与发货，以各 SKU 的基准和实盘时间对齐系统 `on_hand` 与实盘值，保留该期间实物进出的数量、实际发生时间、来源及补录状态；已售未发货商品仍在实物盘点范围。只增加销售占用的事件不等于物理出库，不能在盘点推算中重复减去。不能将盘点开始时的旧余额与盘点结束时的实盘值直接比较或覆盖当前余额；管理员须确认期间变动已核对，并以不重复计入这些变动的差异增量生成纠正流水。迟到事件、未知变动、在途搬动造成计数存疑时保留待核对，必要时复点该 SKU，禁止自动纠正。纠正操作使用版本校验，重新核对占用、安全库存及渠道配额，保留基准、实盘值、变动依据、原因和操作人，不覆盖预留或销售占用。

1. **并发预留**：Shop 同一 SKU 配额只剩 1 件，两次结账同时请求。通过 Core 余额/已生效额度事务锁及版本，只能成功预留一次；另一次返回缺货。
2. **重复事件**：Shopee 同一订单行的库存事件到达两次，第二次命中来源店铺 + 外部行/事件 ID 的唯一键，不再新增占用或流水。
3. **上线前旧订单**：安排可短暂停售的切换窗口。停售后盘点实物在库；已售未发货商品仍在仓内，逐 SKU 导入这些订单行的占用，记录店铺、订单行 ID 和切换时间。之后补拉到相同订单行时只更新必要的状态，不新增第二笔占用。只有盘点、旧订单占用、安全库存和配额对齐后，才逐渠道开放自动同步并恢复销售。
4. **乱序取消**：取消事件先于创建事件到达，先记录待核实并从平台补拉订单最终状态；不能根据事件到达顺序推断订单真实状态。
5. **Shop 支付超时**：预留 2 件已释放，但 Shop 后来通知支付成功。Inventory 不自行判断付款或退款；持久接收销售事实，按已核实映射记录需求，标记待核对并停止该 SKU 新增分配，不复活旧预留，让 Shop 核查履约。需求不足时明确记录缺口，不丢事件或把实物扣为负。
6. **退货**：市场平台显示退款成功但包裹未到，Inventory 不加库存；实物检验 1 件可售、1 件损坏后，在库增加 2、不可售增加 1，新增可售 1 先进入未分配量，不能漏记仍在地点内的损坏物品。
7. **配额调整**：某 SKU 可分配 7 件，三个渠道配额 3/2/2；商户把 Shopee 配额改为 5 时，总额 9 超出 7，应拒绝或要求先降低其他渠道配额。
8. **提高安全库存**：某 SKU 在库 10 件、已占用 2 件，配额合计 8 件；安全库存从 0 改为 2 后，新可分配量 6 件。Inventory 停止新增 Shop 预留，标记超额 2 件，要求减配额和核实平台写入；已存在占用不被悄悄撤销。
9. **人工改库存**：只有 Acuven 管理员的请求能写入；需提供原因，事务内写入库存流水和旧/新数量审计记录，再校验安全库存与渠道配额并触发同步。其他角色收到拒绝结果。
10. **Inventory 不可用时 Shop 仍收款**：Shop 在自己的事务中保存订单及“未完成库存核对”内部标志，使用稳定订单行 ID 写入待补交队列，继续正常收款并告警；不得伪造 Inventory 预留成功。Inventory 恢复后先核对该订单是否已入账，再补交一次库存动作；若可用量不足，保留冲突并交人工处理，不让库存余额悄悄变负。顾客付款前不增加库存待确认提示。人工发现缺货后 48 小时内联系顾客处理。
11. **Shopee 未获接口权限时的人工配额**：盘点 10 件、无不可售与旧订单占用，安全库存 2 件，给 Shopee 卖家后台 4 件、真实 Shop 4 件，TikTok Shop 0 件。Shopee 售出 1 件后，卖家后台可售变 3；管理员在每日不少于两次的核对中按稳定订单行 ID 登记占用，Inventory 中 Shopee 剩余人工份额变 3，Shop 仍最多卖其独立的 4 件。登记前也不能把 Shopee 份额转给 Shop；重复登记不重复扣减。单纯当次核对逾期仅在后台显示，不发 Telegram，不自动转移人工份额或停售；实际核对发现数量冲突时，停止受影响 SKU 自动增配并按严重异常告警。接口获批后的补拉命中相同订单行时只补状态，不再占用一次。

## 5. 状态机、幂等与失败处理

Shop 库存预留状态建议为 `active → committed | released | expired`；市场平台事件映射为“占用、释放、出库、实物入库”等库存动作。Inventory 不复制完整订单或支付状态机；状态转换检查前置条件与版本，并保留库存事件历史。
Shop 另存 `inventory_check_pending` 等内部标志，标识故障期间已付款但未取得 Inventory 预留的订单。该标志不能当作 Inventory 库存已扣减或可履约证明；恢复后由稳定订单行 ID 幂等补交和对账，结果为库存冲突时由人工决定履约或售后。

- 外部库存写入使用店铺 + SKU + 目标版本/数量的稳定幂等标识；超时且不知道平台是否成功时读取平台库存并补拉/核对期间销售，再决定是否重试；单次回读相同数量不能证明没有并发销售，也不能据此盲目重发旧目标增加库存。
- webhook 验证签名与时间、确定对应店铺，只保留必要的库存字段并快速回应；异步消费者按外部事件 ID/订单行去重。没有可靠事件 ID 时按业务唯一键兜底。
- 每个连接维护独立限流桶、退避和断路状态。补拉按平台可用的时间窗口分段进行，不得把轮询当作无限制实时接口。
- 市场平台可能已在其自身库存中扣除新订单数量。适配器须核对平台返回的是“总量”还是“剩余可售量”，并按店铺与订单行记录已处理的占用；向订单来源店铺回写数量时不得把同一笔销售再扣一次，其他渠道仍按中心库存传播新可售量。
- 定期核对各渠道 SKU 数量、未处理库存事件与实际盘点；差异标识“本地多/平台多/映射错误/权限不足/平台限制”。运营员可调查和提出调整建议，只有 Acuven 管理员可确认会改变库存数量或配额的处理。Inventory 不对账资金或物流。
- 同步失败、授权失效或可能超卖时，将异常记录到后台告警队列并发送独立库存运营 Telegram 机器人或群组的管理员通知，不能复用 OpenClaw 开发任务通知通道。可能超卖等严重异常全天发送；同一未确认严重事件每 15 分钟重复提醒，直至 Acuven 负责人确认，确认时间与操作者留痕，避免每次重试生成新的独立告警。确认只停止重复提醒，异常仍保持待处理，直到库存核对或连接恢复并记录处理结果。当前没有备用负责人；首次严重告警发出 1 小时仍未确认时后台记录超时，仅继续提醒本人，不转发给其他人。已上线 Inventory 临时故障时，负责人在首次严重告警送达后 1 小时内记录“继续接单或人工停售”的决定；没有决定时后台继续显示超时待办，但不会自动停售。普通异常每天按 Asia/Kuala_Lumpur 09:00–18:00 发送，周末和节假日相同；后台始终记录所有异常，升级为严重异常后立即按全天规则提醒。通知携带店铺、SKU、异常类型、发生时间和处理链接，不包含渠道令牌、顾客资料或支付信息。通知失败须可重试并在后台标明未送达。
- 检测到平台后台直接改库存导致的数量差异时，将受影响的店铺规格置为 `needs_review`，告警并暂停其自动同步及自动增配，但不自动停售或改写平台库存。保留平台读数、Inventory 期望值和最近一次成功写入记录；运营人员核对实物、未发货占用与平台销售后，填写原因并确认修正，再恢复同步。不得自动把平台数量当作实物在库，也不得未经核对覆盖平台数量；如需降低可售量，由运营负责人手动决定并核实平台结果。
- 库存同步传播期间仍可能超卖；可配置安全库存，并在告警面板展示实际传播时长。不得承诺绝对零超卖。

### 5.1 首批自营渠道的防超卖规则

首批 Shopee、TikTok Shop 与真实 Acuven Shop 采用**按 SKU 固定渠道配额 + 安全库存**。例：盘点确认实物 10 件、无其他占用，留 2 件安全库存，剩余 8 件可分为 Shopee 3、TikTok Shop 3、真实 Shop 2。任何配额调整先在 Core 的政策/额度事务检查总额，再写渠道，确认平台写入结果；未确认时不把新增数量分给别的渠道。不设自动集中销售的数量阈值；仅剩 1 件可分配时，整数配额不能把同一件分给多个渠道，具体渠道由既定分配或管理员决定。
在 Shopee 应用权限尚未获批、仍继续销售同一 SKU 的过渡期，Shopee 份额在卖家后台人工设置并在 Inventory 标记为 `manual_quota`；真实 Shop 只能用独立份额。管理员在每个仍在售的自然日最少核对两次 Shopee 销售与未发货占用，登记最小事件与核对时间。用户已选择本人无法按时核对时继续销售并接受超卖风险；单纯逾期只在后台显示未核对区间与风险，不推送 Telegram，也不自动增配、转移 Shopee 份额或停售。实际核对发现数量冲突、配额超限或可能超卖时，转为严重异常并按全天主动提醒规则处理。TikTok Shop 尚未开始真实销售且接口未就绪时配额为 0。相关业务验收见[需求文档](REQUIREMENTS.md)第 4.1、4.3 和 4.4 节。

控制台在每个 SKU 库存行提供“安全库存”编辑项，新行预填 2 件，显示在库、Shop 预留、已确认销售占用、不可售、安全库存、可分配量与三渠道配额。写入接口校验角色和非负整数，使用版本号防止管理员覆盖彼此修改；保存审计事件并触发配额校验与渠道同步。安全库存是业务配置，不直接产生实物出入库流水。

期初盘点、SKU 映射与平台当前订单全部核实后才开放自动同步。渠道后台直接改库存或人工接单属于外部变更，须补拉与对账；尽量由 Inventory 作为唯一库存编辑入口。市场平台自行扣掉本店订单数量时，不能再把同一笔订单对该平台写成“二次扣减”。[TikTok Shop 的库存写入接口](https://partner.tiktokshop.com/docv2/page/update-inventory)明确按 SKU/仓库写数量，且可能因仓库权限、共享库存或促销锁定而拒绝更新；所以每次写入必须逐 SKU 检查返回的错误，不能只看请求整体成功。Shopee 的具体能力待获批应用后台及真实店铺验证。

**已确认的异常处置**：授权失效、写库存失败、销售事件漏同步、负库存或映射不明时，停止该 SKU 的自动增量分配并立即告警；不自动停售 Shop 或市场平台商品，也不自动向平台写 0 库存。Inventory 可用时 Shop 仍按正常规则请求预留；Inventory 不可用时 Shop 继续收款，内部标记未核对、持久排队并告警。运营负责人收到告警后人工判断是否停售、调整平台库存和处理无法履行的订单。恢复自动同步前重新盘点并对账；页面持续显示超卖风险。安全库存 2 件不保证故障期间不超卖。

## 6. 平台适配器与权限核验清单

真实平台首次启用遵循用户确认的当天核对策略：所需接口获批且权限、映射、实物及已售占用、安全库存、配额、库存读写与事件核对通过后，可当天启用该平台全部已确认 SKU，不设置强制多日只读观察或仅少量 SKU 写入的业务门槛。启用任务逐 SKU 持久记录平台请求及实际确认结果，批量任务提交成功不代表各规格均已生效；失败或结果不明的 SKU 保持待核对，不能重复叠加增配。开发、测试和上线前核对仍须满足既定验收条件，未获批权限与未确认规格不随批次启用。

适配器首批只需 `authorize/refresh`, `import_skus`, `read_stock`, `pull_inventory_events`, `apply_stock`, `handle_webhook`, `capabilities`；其中订单 API 仅提取改变库存的 SKU、数量和状态，不构建完整订单模型。每个写入返回“已确认成功、明确失败、结果未知、不支持”之一；不得把不支持吞成成功。

### 6.1 第零阶段：先取得开发者准入

实际申请入口、可复用文案、最小权限清单及当前阻塞见acuven_hub 私有仓库的 `inventory/ACCESS_APPLICATIONS.md`（经营信息，不放进本公开仓库）。

这是本项目**第一个实际任务**，优先于平台适配器编码。Shopee 与 TikTok Shop 自营店铺均已开通，且属于同一马来西亚经营主体；Shopee 有真实订单，TikTok Shop 暂无订单。目前三个平台均无开发者权限。两平台现在都按第三方开发者类别申请，但首批只授权 Acuven 自营店；Lazada 作为后续阶段，不阻挡首批上线。负责申请的运营者按平台完成以下清单，并在不保存密钥的台账里记录证据：

1. 确认平台官方开发者入口、马来西亚可申请的账户/应用类别，以及“供多家商户授权”的连接器或服务商条件；准备平台要求的公司、产品、隐私与安全资料。
2. 按库存业务申请最小必要权限：店铺授权、商品规格、库存读写、读取会改变库存的订单行/取消/退货状态、webhook。首批不申请聊天、收款、物流打单等与 Inventory 库存无关的权限；未获批的能力在产品中标为不可用。
3. 创建应用，取得测试环境或开发店铺资格；确认至少一个有权授权的店铺。记录应用审核状态、权限范围、授权有效期、测试环境限制和平台支持渠道。
4. 获批后验证授权、读取规格与库存、读取最小销售变动、写库存、接收事件；记录实际限流、错误码和同步延迟。只有测试通过才把对应适配器任务解除阻塞。

Shopee 第三方资格申请的实际表单强制要求**可访问的正式业务产品 URL 与测试账号密码**；审核意见、更正经过与当前状态记在acuven_hub 私有仓库的 `inventory/ACCESS_APPLICATIONS.md`。若后续应用审核要求新 Inventory 演示，应提供与生产数据隔离的最小 Inventory Demo 和可撤销的审核账号。审核账号不得接触生产店铺、库存或平台令牌。Shopee 表单另有安全报告步骤：申请未遮蔽敏感个人资料时才要求渗透测试报告；首批库存应用不申请该权限。

### 6.2 TikTok Shop 授权回调地址

TikTok Shop 创建应用时的 `Enable API → Redirect URL` 是卖家授权后的**授权码接收地址**，不是商品页、Shop 首页，也不是库存事件 webhook。Inventory 的 FastAPI 后端在 `GET /api/v1/integrations/tiktok-shop/oauth/callback` 接收，由 Inventory 独立的公开 HTTPS 子域名承载（子域名只配在服务器与 GitHub 变量里，不写进本仓库），拟填的完整地址形如 `https://<Inventory 子域名>/api/v1/integrations/tiktok-shop/oauth/callback`。**该子域名和路由从外网验证可用之前，不应提交。**

用户确认自己可以配置 Inventory 子域名与 HTTPS；下一步由用户配置 DNS/反向代理，项目实现并部署回调路由后，从外网验证实际响应，再填写 TikTok Shop 表单。当前尚未完成配置。Demo 与生产使用不同域名和应用凭据，授权回调不能跨环境。

授权开始时由后端生成不可预测、短期有效且一次性使用的 `state`，绑定发起连接的管理员会话与目标店铺。回调收到 `code` 后先校验 `state`、错误参数及所属环境，再由后端使用应用凭据兑换令牌，并加密保存店铺令牌及获批 scope；成功后跳转到不含 `code` 的后台结果页。授权码、应用密钥和令牌不得出现在浏览器持久化日志、仓库或客服会话。Webhook 是另一条独立 URL，需另行配置与验签。提交前从外网测试 HTTPS、路由可达及反向代理转发，真实授权前完成全流程联调。Partner Center 当前页面写明 Redirect URL 可在提交后编辑，但修改后须确认授权链接与配置一致。

## 7. Demo 与真实 Shop 的边界

### 7.1 两个部署与库存协议

1. 已确认 Acuven Shop 同一代码库部署 Demo 与真实站两套环境：各用独立数据库、域名和配置。Demo 不配置真实支付凭据，只用模拟支付和示例库存；真实站持有自己的支付账号，不运行每日演示库存重置。两套环境的数据与令牌不可互通。
   Inventory 同样区分独立的 Demo 与真实部署：Demo 只接模拟店铺和示例库存事件，不保存或使用 Acuven 生产渠道令牌，所有演示页面标注 Demo。Demo Shop 只与 Demo Inventory 的示例库存交互。
   潜在顾客首期共用一个 Demo 登录账号；服务端强制该账号仅访问示例环境，不授予真实店铺授权、生产库存或凭据查看权限。账号可编辑示例库存与安全库存；独立的重置任务每周恢复预置数据，管理员也可手动触发，重置不得触及真实环境，并在界面告知共享数据可能被其他使用者修改或重置。
   Demo 的主要转化动作是预约与 Acuven 进行产品演示或洽谈。用户确认独立商务预约 WhatsApp 号码已可正常收发消息；演示流程结束处的按钮打开该号码，并预填预约意图，不复用真实店客服和行业 Demo 共用的客服入口。按钮目标号码由部署配置提供，不写入共享演示账号可读取的预约记录；Demo 每周重置不应影响预约对话。
2. 真实 Shop 保留顾客、购物车、价格、优惠、运费、税费/发票、订单、支付、物流及售后。Inventory 提供 SKU 可售查询与带 TTL 的原子预留；Inventory 故障时 Shop 按已确认的例外规则继续接单收款，并内部标记待库存核对。
   首批商品为 3C 电子配件，包含内置电池商品，但没有单独电池或移动电源。资料以现有 Shopee 商品为基础导入，并逐项核对名称、图片、描述、颜色/尺寸、品牌或兼容性表述、包装内容与 Acuven SKU；Shop 自行设定售价和运费，不把 Shopee 价格当作权威。Shopee 开发者权限尚未获批时，使用卖家后台导出资料或整理好的商品表格与图片导入，逐项核对后发布，不等待商品 API。Shop 商品记录应标明内置电池及承运限制，未核实可寄送路线的型号不开放真实结账。
   首批还包含无线功能型号；用户确认每个首批型号的 SIRIM／MCMC 资料均已备齐。Shop 发布清单仍需为每个适用型号记录认证/标签的实际核对状态与依据，在经营者逐项确认之前不开放该型号的真实结账。库存 Inventory 只保留与 SKU 和可售量相关的引用，不存放认证证件或供应商敏感资料。
   用户确认首批商品只使用自有或无品牌标识，不在标题、图片或包装沿用第三方商标。商品导入审核检查品牌字段和素材，避免把 Shopee 原有资料未经核对直接发布到真实 Shop。
3. 正常路径下，仅在顾客提交订单并准备进入付款页时，Shop 服务端校验订单行和数量，以自身幂等订单引用创建 Inventory 预留；加入购物车、浏览商品和填写地址不调用预留写入。预留有效期为首次成功预留起 30 分钟，Inventory 返回并持久保存到期时间；重复请求或页面刷新不得产生第二份预留，也不自动延长期限。支付服务端确认后通知 Inventory 把预留转为已确认销售占用，失败或超时则释放。Shop 根据实际服务商配置支付会话有效期、显示付款期限并核验过期会话与付款中状态；迟到付款仍走库存核对流程，不假报原预留有效。若结账时 Inventory 不可用，Shop 不伪造预留，而是在自身数据库持久记录已付款订单及待补交库存事件；恢复后幂等核对，缺货交人工。Inventory 只保存引用、SKU、数量及动作，不保存金额和顾客资料。
4. Shop 发货时通知 Inventory 把已占用量转为物理出库；未发货取消释放占用；退款不直接返库，验收实物退货后才发送入库事件。迟到支付或结果未知由 Shop 核实，Inventory 标记库存冲突并暂停该 SKU 新增配额。
   首期处理整单全额退款和按订单行/退回数量计算的部分退款。退款申请在 Shop 由人工审核，只有审核通过的申请才由 Shop 服务端计算可退金额并调用支付服务商的已验证退款接口；累计退款不得超过原实收金额，重复请求、人工重试和服务商回调须幂等。保存订单行、退回数量、已退金额、幂等请求标识、服务商结果与失败待办；客服不能越过审核直接退款，Inventory 不参与资金动作。
5. 旧演示订单只留在 Demo 数据库，不导入真实订单。真实站上线前单独完成支付、配送、售后和回退设计。

已付款订单首期不提供商品规格或数量变更接口；未发货时按既定规则取消，再以新订单引用重新定价、申请库存和创建支付会话。旧订单引用、库存动作及付款记录保持可追溯，不能复用旧预留或将新付款抵作旧退款；取消与原单退款人工审核的边界沿用已确认流程。顾客改单能力只覆盖既定的地址修改及取消。

待付款订单修改商品或数量采用取消旧单、建立新单的流程：Shop 先查询并确认支付状态，作废旧支付会话成功后幂等释放旧库存预留及未付款名额，再重新校验购物车、定价和建立新预留／支付会话。用关联记录连接旧、新订单，禁止原地更改旧预留的订单行或金额。关闭会话失败或支付状态未知时显示待核对，不假报已作废；旧单已支付时转为已付款订单规则。超时或迟到付款仍按既定流程处理，不删除旧订单、付款引用或库存流水。

**待 Shop 项目正式设计的事项**：真实支付和退款、优惠与积分、马新运费及币种、税费/发票、支付成功但库存预留已过期的处置、Demo/真实环境切换与回退。真实站的隐私告知、配送、取消/退货退款和服务条款目前均无正式版本；Shop 仓库须另列内容编写、经营者核对、结账前展示与发布验收任务，隐私告知准备马来语和英语版本。当前支付服务商尚未选定；若选择 Stripe，用户决定复用当前 Acuven Technology 账户同时收开发服务费与 Shop 商品款，并已确认两类业务由同一马来西亚经营主体承担，Stripe 业务资料仍须核实。两家账户的实际状态见 acuven_hub 私有仓库的 `inventory/PAYMENT_APPLICATIONS.md`。Inventory 不决定金额。
自愿“改变主意”退货已确定为收货后 7 天内可申请，收货日以承运商显示的签收日期为准，有争议时人工核实；申请获准后 7 天内寄出，以寄件凭证或承运商首次揽收时间判断。退货送达 Acuven 后，人工在 48 小时内验收并告知顾客是否批准退款，周末和节假日照常计时；验收条件为未使用、配件齐全、无损坏，允许拆包合理检查。顾客承担退回寄件费用，原订单已付配送费不退；故障或错发另行处理。Shop 须记录承运商签收日期与争议核实结果，以及申请、批准、寄出、送达、验收和结果通知时间，以及证据与审核人；验收通过后才执行已审核的退款。退款审核通过后 24 小时内发起原路退款，周末和节假日照常计时；Shop 跟踪提交时间、支付服务商受理和最终结果，向顾客区分“已发起”与“已到账”。多件订单只退部分商品时，Shop 按实际退回的订单行和数量发起部分退款，不得把单件退货直接送入整单全额退款接口。整单优惠按各订单行原价金额占比分摊，退款取该行实际支付价款中尚未退回的部分；用最小货币单位计算并确定性处理尾差，使各行优惠合计等于整单优惠，且累计退款不超过原实收金额。
真实 Shop 的接单闸门要求正式在线支付商户账号和支付链路通过上线验收。正式上线前若仍未完成证件审核、所需付款方式启用及收款/退款/提现验证，Demo 照常开放，真实站不得创建需履约的新订单，待支付可用并验证后才开放结账；不以银行转账订单替代已确定的在线支付流程。
接单闸门还要求 Inventory 的 SKU 映射、期初盘点、正常预留与库存事件链路通过验收。若 Inventory 尚未达到首次上线条件，Demo 先开放，真实 Shop 暂不接单；第 4.1 节的故障期间继续收款仅用于已正式上线后的临时 Inventory 不可用，不用于把未完成的 Inventory 当作已上线。
马来西亚境内已有可行的寄送方式，但物流账号尚未开通；用户确认该人工寄件方式可寄送首批内置电池商品，了解申报及包装要求，并明确覆盖西马、沙巴和砂拉越。首批接单范围包括这三个地区；Shop 须按收件邮编、商品及具体路线核对承运条件、运费和预计送达时间，不支持的地址或商品组合不得开放结账。Shop 结账前按地区与商品重量计算并显示订单应付运费；在尚无物流实时报价接口时，由运营维护经承运方式核实的地区、重量分段与费用表，结账服务端保存所用运价版本及金额快照。首批商品的含包装重量和尺寸仅有部分资料，运营须在开放各商品结账前称重测量缺失项目并核对现有值；商品包装后重量、尺寸或适用运价缺失时不得猜测运费，应先补齐数据或关闭该组合的结账。人工寄件的实际承运收费高于订单运费快照时，Shop 不产生补款请求，由 Acuven 承担差额；实际收费较低时仍按订单快照收费。Shop 可记录运费差异，运营定期据此修订价表，仅影响之后的新报价。已付款且库存可用的订单，Shop 须以支付确认时间为起点跟踪 48 小时交运期限，周末和节假日照常计时；超时进入运营待办并记录原因。首批 Shop 由运营人员人工办理寄件并在 Shop 录入物流单号，保存承运商、单号、交运时间、录入人和录入时间；自动打单后续接入。新加坡跨境物流账号和明确的寄送方式也尚未具备；在跨境履约能力未准备好时，真实 Shop 先只接受马来西亚订单。新加坡结账在服务端保持关闭，不能只隐藏前端按钮；开放前必须确认可实际履约的线路、运费、交付时间和退货路径。库存平台不代办该项。
真实 Shop 首期必须覆盖银行卡/信用卡、马来西亚 FPX 和 Touch ’n Go eWallet，仅接受西马、沙巴和砂拉越的 MYR 订单；结账页须明确显示 Touch ’n Go eWallet 选项，仅有通用 DuitNow QR、GrabPay 或卡绑定钱包均不能替代。新加坡订单及 SGD 收款属于后续阶段：届时 SGD 商品售价由 MYR 基础售价按实时汇率自动换算，Shop 在顾客开始结账时锁定 SGD 应付金额一段时间，超时重新报价；锁价期限应与支付会话、Inventory 库存预留期限协调。Shop 还需明确可信汇率来源、更新时间、舍入、汇率服务故障及退款原币种规则；Inventory 不获取汇率或金额。首期支付服务商筛选以三类 MYR 付款方式的实际可用性和退款流程为上线条件，SGD 能力单列未来核验，不阻塞马来西亚上线。Stripe 当前商户账户能否直接受理 Touch ’n Go eWallet 尚未证实；Billplz 官方列出该钱包但仍需商户 KYB、启用和实测。

### 7.2 真实 Shop 的支付候选（不属于 Inventory）

Shop 服务端对同一已登录顾客或同一服务端识别的访客浏览器会话，原子校验最多 3 笔有效且占库存的未付款订单，防止并发打开付款页绕过名额限制；重试按订单幂等键复用。已付款、取消或库存预留到期后释放相应名额。顾客／访客身份留在 Shop，Inventory 仅接收库存操作所需订单引用及连接身份。访客会话并不等于已验证顾客身份，仍须配合结账接口限流；不以未经验证的订单手机号作为可靠身份限制依据。

库存预留到期须与支付会话生命周期协调。[Stripe Checkout 的 `expires_at`](https://docs.stripe.com/api/checkout/sessions/create)允许在支付会话创建后 30 分钟至 24 小时之间设置，默认 24 小时；不能不加配置就让较短库存预留与默认支付页长期并存。[Billplz 的 `due_at`](https://support.billplz.com/api)仅表示账单日期，不影响账单是否仍可付款，不能作为自动关闭支付的依据。Shop 必须按最终服务商验证关闭未付款会话、查询支付中状态与处理迟到付款的链路；无法阻止旧支付页付款时须保留已确认的迟到付款人工核对流程，不假报订单已确认库存。

用户决定同时申请 Stripe 与 Billplz 的正式商户账号，待账户验证、已启用付款方式和退款流程核实后，再选定正式接入方。若选择 Stripe，Shop 与开发服务费复用当前 Acuven Technology 账户，不另为 Shop 开户；两类业务同属一个马来西亚经营主体已由用户确认，商户业务说明、网站、顾客可见收款名称及服务商要求仍须逐项核对。两家商户账户的实际状态记在 acuven_hub 私有仓库的 `inventory/PAYMENT_APPLICATIONS.md`。2026-10-06 核对的公开资料只用于初筛；实际费率、准入和已启用付款方式以商户后台及合同为准。
申请步骤与当前状态见 acuven_hub 私有仓库的 `inventory/PAYMENT_APPLICATIONS.md`。

## 8. 内部 API 草案

以下业务语义与 v1 最小契约草案用于实现任务和联调验收，当前尚无已实现接口；实现时由 OpenAPI 明确请求／响应结构，并验证与本文规则一致。所有写入都需服务身份、权限、请求 ID 和幂等键；Demo 环境不能调用真实写入接口。

网店整单预留接口一次接收该订单的全部 SKU 与数量，由 Core 在唯一数量事务中校验已生效入口额度并占用；同一 SKU 的重复行先合并数量，避免每行单独校验造成超额。任一项不足则整个请求失败并返回缺货项，不留下其他项的有效占用，Shop 不创建可供顾客付款的支付会话。并发锁按稳定 SKU 顺序获取，重试复用整单预留标识；具体字段见 API_CONTRACT 的 v1 评审草案，批准后冻结。库存不足、无效映射、无权操作等业务失败不得冒充连接故障而进入继续收款例外。批量预留验收须包括“两项订单、一项无货，无任何部分占用”与整单请求重试不重复占用。

| 调用方 | 操作 | 返回与边界 |
| --- | --- | --- |
| 真实 Shop → Inventory | 查询 SKU 可售、创建/查询/释放预留 | 可售结果已扣安全库存；返回版本号、有效期及库存不足原因。 |
| 真实 Shop → Inventory | 发送确认销售、未发货取消、出库、实际退货入库事件 | Inventory 按 Shop 事件与行 ID 去重，只更新库存。 |
| Inventory → 真实 Shop | 库存不足、预留过期、同步异常响应/通知 | Shop 决定如何处理订单和顾客，不把 Inventory 当付款权威。 |
| Chatbot → Inventory | 查询商品规格与库存 | 面向顾客的工具只返回该网店授权范围内的规格和有货／售罄状态，不返回具体剩余数量、其他连接配额、订单或顾客资料。 |
| Chatbot → 真实 Shop | 登录绑定后查本人订单、经 Shop 结账代下单、未发货改单/取消 | Shop 服务端重算价格并验证顾客、订单归属和最新履约状态；订单库存动作再由 Shop 发给 Inventory。 |
| Chatbot → 真实 Shop 人工售后队列 | 发起退款申请 | 只生成待人工审核请求；AI 不调用支付退款接口。市场平台订单遵守平台内买家身份与售后流程。 |
| 平台 → Inventory | 各店铺授权回调和 webhook | 验签、找店铺、持久化、异步处理。 |

v1 的路径、精确字段、scope、响应示例、引用查询、错误及重试规则在 [API_CONTRACT](API_CONTRACT.md)中细化；本节表格只作概览。数量查询与顾客状态查询采用不同受限端点，Inventory 不提供查完整订单的 API。路径仍是拟实施契约，不能当作现有接口。

另提供 `GET /internal/v1/connection`、`GET /internal/v1/mappings` 作本网店只读接入发现；请求身份固定连接，服务端不接受自选归属。接入规范细化连接器能力与安全边界，OpenAPI 设计现已保存，待实际实现、CI 和接入验收。

区分 Shop 服务端结账所需的数量响应、管理员库存视图及顾客可见的库存状态。Shop 后端可以得到自身连接的可售件数用于原子预留；商品页公开响应和 Chatbot 顾客工具仅返回授权连接的可用状态，不将完整数量或其他连接份额传给浏览器或大模型再靠提示词隐藏。缺货项提示用于调整购物车，不能将页面曾显示有货当作本次已预留的证明；内部查询结果不明时按既定库存故障流程处理，不编造数量或库存确认。

### 8.1 v1 最小库存契约草案

服务调用通过 HTTPS，`Authorization` 只承载部署环境保管的服务凭据，凭据绑定连接、环境及最小操作权限。每次调用带 `X-Request-ID`；写入还须带 `Idempotency-Key`。连接身份由服务端验证并绑定，调用方不得指定另一个连接绕过权限。后台管理员与顾客工具各用受限身份；顾客浏览器不持有 Inventory 写入凭据。时间用 UTC 的 RFC 3339 值，界面按马来西亚时间显示；数量为正整数“件”，中心 SKU 不代替授权检查。

| 路径草案 | 最小请求字段 | 结果与约束 |
| --- | --- | --- |
| `GET /internal/v1/availability` | 已映射 `sku_id`，批量使用重复 query 参数；精确结构见 API_CONTRACT | Shop 服务端得到自身连接的 `availability_state`、`available_quantity`、`stock_version`、`as_of`。数量按本连接配额及中心约束计算；未知状态不能伪造成 0 件或有货。顾客／AI 身份只得到状态与授权规格，不得到数量。 |
| `POST /internal/v1/reservations` | 稳定 `order_ref`、`lines[]`，每行含 `line_ref`、`sku_id`、`quantity` | 整单成功返回 `reservation_id`、`state=active`、`expires_at`；有效期首次预留起 30 分钟。同 SKU 多行先合并校验但保留订单行关联。缺货整单失败，返回缺货项而不留下部分占用。 |
| `GET /internal/v1/reservations/{reservation_id}` | 路径中的预留 ID | 返回本连接的预留状态、订单引用和到期时间；不得查询另一连接的记录。供超时核对及重试判断使用。 |
| `POST /internal/v1/reservations/{reservation_id}/release` | 释放原因及幂等键 | 仅释放可释放的待付款预留；重复释放返回原结果。已转销售占用的记录须通过对应取消事件处理，不能再按待付款预留释放。 |
| `POST /internal/v1/inventory-events` | 稳定 `event_ref`、`order_ref`、`action`、`occurred_at`、`lines[]`；每行含 `line_ref`、`sku_id`、`quantity`，已有预留时带 `reservation_id` | 持久接收后返回事件 ID 和 `received` 状态；受理不等于库存动作已完成。允许确认销售、未出库取消、实际出库和验收后的实际退货入库；不接受“退款成功”作为加库存动作。 |
| `GET /internal/v1/inventory-events/{event_id}` | 路径中的事件 ID | 返回本连接事件的 `received`、`processed`、`needs_review` 或 `failed` 状态及脱敏原因；Shop 用于核对与补偿。 |

`order_ref`、`line_ref` 和 `event_ref` 使用系统标识，不嵌入顾客联系方式或付款资料。写入只接受库存协议白名单字段，Inventory 不接收价格、顾客姓名、电话、收货地址或支付凭据。首次接收真实销售事实若无有效预留或库存不足，保留事实并进入差异核对，不能丢弃已付款订单对应事件或把库存悄悄扣成负数。

| HTTP／业务结果 | 调用方处理 |
| --- | --- |
| `400/422 INVALID_REQUEST` | 修正数量、格式或字段；不得继续收款作为兜底。 |
| `401/403 UNAUTHORIZED / FORBIDDEN` | 处理服务身份、环境及连接权限；不得当作普通网络故障。 |
| `409 INSUFFICIENT_STOCK` | 整单不进入付款页，提示顾客调整购物车。 |
| `409 RESERVATION_EXPIRED / STATE_CONFLICT` | 核对预留及订单最新状态；已付款事实进入库存核对，不自动复活过期预留。 |
| `409 IDEMPOTENCY_CONFLICT` | 同一键携带不同内容，拒绝覆盖原操作；修正客户端逻辑。 |
| `409 CONNECTION_DRAINING / MAPPING_REVIEW_REQUIRED` | 禁止新预留，按存量交接或 SKU 映射核对流程处理。 |
| `429 RATE_LIMITED` | 按返回的重试信息退避，不用新的幂等键重复占用；不作为故障继续收款的依据。 |
| 网络超时或服务不可用 | 超时不代表写入失败；优先查询原结果或用原幂等键重试。确实无法核对时，Shop 按已确认的临时故障流程持久记录待补交事件并告警，不伪造预留成功。 |

事件的 `action` 草案为 `sale_confirmed`、`sale_cancelled`、`dispatched`、`return_received`；每个动作均须校验该连接订单行的已有数量和状态，重复事件不重复占用／释放／入库。按连接与操作范围保存幂等键和请求内容摘要，同键同内容复用结果；同时以连接和稳定订单行／事件引用防止换键造成同一业务重复处理。失败或未明结果的重试不重建新的订单引用。正常响应状态、字段及错误码须在实现后的 OpenAPI 和两个隔离环境联调中验证，不能仅以文档列出视作实现已通过。

### 8.2 客服登录与售后边界

客服的“先登录”建议采用 Shop 官网登录后签发一次性会话绑定凭证：顾客在可信浏览器完成登录，再把当前聊天会话与该顾客账号绑定，凭证短期有效且可撤销。不能把 WhatsApp 号码、聊天昵称或顾客在对话中输入的账号密码当作登录。每次改单都由真实 Shop 服务端验证会话、订单归属及最新发货/运单状态；已创建但未交运的面单需先作废或更新，才能改收货地址。退款申请进人工审核队列，AI 不调用支付退款接口。
真实 Shop 首期允许访客下单；客服的登录要求只适用于通过 AI 客服执行本人订单操作。访客订单须在顾客登录后，向订单手机号发送一次性短信验证码并完成验证，再绑定到该账号；验证完成之前，AI 客服不得仅凭聊天号码或订单号自动归属。认领接口须记录一次性验证结果、订单与账号的绑定及审计事件，防止同一订单被多个账号认领。
生产短信验证码服务账号目前尚未开通；Shop 的会员登录、订单认领及客服会话绑定联调需等开户并验证马来西亚号码真实送达。未验证前不能把模拟验证码链路视作生产可用。
若短信服务延迟，真实 Shop 可先开放访客下单，但须以功能开关在服务端关闭会员订单认领和 AI 客服订单操作，待短信及登录链路验收通过后再启用。此期间不提供访客在线自助取消/退款申请；订单确认页和通知须提供与 AI 客服共用的 WhatsApp 入口，AI 识别售后请求后转人工。人工客服先回拨订单原填写手机号核实申请人；多次无人接听时交 Acuven 管理员核对其他订单与付款证据并决定，不能自动通过或拒绝。Shop 售后记录保存回拨结果、备用核验依据、决定、处理人和时间；核实前不向请求者披露订单资料或执行取消/退款。付款证据只在 Shop 的受控售后流程处理，不提供给 AI 或 Inventory；AI 不代替人工核验或执行退款。
真实店售后队列须记录 WhatsApp 取消/退款请求进入人工队列的时间和首次人工回复时间；以入队时间起 24 小时为首次人工回应期限，每天均计入，包括周末和节假日。到期未回复显示逾期待办；不把自动回复或 AI 回复计作人工首次回应，也不把回应等同于审核通过或退款完成。
真实店铺首期复用 `ai_chatbot_demo` 现有 Demo WhatsApp 号码。新对话默认进入真实店客服；Demo 访客通过专用演示链接或菜单进入。真实店与多行业 Demo 必须采用服务端明确的会话模式及工具授权隔离；不能由大模型自行猜测模式，也不能让演示会话访问真实订单或库存写入。模式切换须清除或隔离上一模式的上下文与授权；人工接管应显示当前模式，避免按演示资料处理真实顾客。

## 9. 测试与上线闸门

- 生产 Inventory 至少保留 30 天可恢复备份及覆盖相应恢复窗口的连续变更记录。上线前在隔离环境完成数据库恢复演练，验证库存、预留、渠道配额、事件去重键与审计流水能恢复到故障前 15 分钟以内的恢复点，并在故障后 4 小时内恢复到可核对库存和处理新销售的状态。恢复后重放 Shop 待补交事件并对账平台销售，确认不会重复占用库存，再逐渠道恢复自动写入。备份与连续变更记录须与生产数据库故障域隔离，Demo 重置不得影响生产备份。
- 真实后台首期按用户选择仅使用密码登录；实现生产管理员独立账号、密码安全存储、登录限流、失败记录、会话失效与账号停用。共享 Demo 登录不能进入生产管理后台，库存及连接变更的审计须记录实际个人账号；不将双重验证列为首期已交付能力。

## 10. 开发任务拆分建议

按 OpenClaw 契约的“单层、小范围、可独立验收”原则，先拆为：

0. **先启动自营 Shopee、TikTok Shop 开发者申请**：由运营者提交并跟踪审核；按第 6.1 节留申请状态和缺项。Lazada 后续申请。这是项目首要里程碑，独立于 Worker 代码任务。
1. 仓库骨架、CI、健康检查与 OpenClaw 契约。
2. 单库存地点与普通规格 SKU 映射、库存余额/流水数据库及迁移。
3. 安全库存默认 2、固定渠道配额、盘点与调整的规则、接口和控制台。
4. 真实 Shop 可售查询、原子预留、释放与最小库存事件；Demo/真实双部署、支付和订单改造在 Shop 仓库独立登记。
5. Shopee、TikTok Shop 各自按“授权 → SKU 映射 → 库存读写 → 最小销售事件 → 对账 → 真实启用”登记；平台审批未过则保持阻塞。
6. 同步异常面板、补拉、告警及真实盘点核对。
7. AI 客服 Acuven 零售工具替换在客服仓库独立登记；库存查 Inventory，订单动作查真实 Shop。

每项会改变库存的任务在变为 `ready` 前写定状态迁移、失败与重试及具体前后数据例子，走模板要求的设计预审。下一步建仓时才创建 machine-readable `tasks.yaml` 与 planning-v1；平台审批未通过的适配器任务列为“已阻塞”。订单管理、资金、物流、多仓、组合装和 SaaS 另作后续设计，不放进首批任务契约。

上面的方向细化为 [DELIVERY_PLAN](DELIVERY_PLAN.md)中的小任务、文件范围、依赖和 CI 门槛。当前未登记任何任务，也未修改 Shop、Chatbot、WhatsApp 网关或控制面；各自改造包与联调证据先形成可审阅交接材料，再在对应仓库实施。

## 11. 系统群依赖、部署与原子性闸门

现行方向见[架构对齐](HUB_ARCHITECTURE_ALIGNMENT.md)和[共享核心决定](decisions/SHARED_COMMERCE_CORE.md)。先完成现有 Shop Demo，定租户/身份/模块授权及 Core 契约/迁移，验证共用核心后再开发 Inventory V1 数量包装和真实 Shop/平台。此顺序只修正文档，不改变现行 Shop/OpenClaw 任务。

Inventory 的 app/persistence 只保存渠道/政策/发布/差异等产品数据，权威 catalog、stock ledger、reservations 数量状态、基础流水/数量迁移归 Core 项目。旧目录结构中的 app/domain 可保留渠道规则，不能按旧草案在本库重建余额/账表。单模块交付随附核心，ERP/门户/AI 可选；三种部署模式的实例/租户/池、升级和本地登录需分别验证。

原稿“同 Inventory MySQL 事务更新所有余额与份额”的前提已取消。建议 Core 一个数量事务执行已生效入口额度/安全政策、H/C、预留、数量去重与流水；Inventory 发命令并查询原结果，保存政策期望和外部发布结果。不能拆成先改本地 Q 再加远端 H 的两个请求。Core 实际接口/并发证据未完成前相关任务保持待设计。

备份、恢复与 Demo 重置覆盖 Inventory 产品库和 Core 账/目录的联合版本/业务水位，异步 ERP/平台已完成事件也可重放对账；只恢复 Inventory 库不足以恢复数量。详见 OPERATIONS 与对齐报告。
