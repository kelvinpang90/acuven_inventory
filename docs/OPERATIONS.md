# 界面、Demo 重置与恢复操作设计

> 版本：1.0 设计草案 · 日期：2026-10-07。提供开发验收和上线操作步骤，当前没有实际部署或备份作业。

写表单携带读取时的版本号；409 版本冲突要求刷新核对后重提，不能自动覆盖。操作提交结果未知显示“待核对”，不能用成功 toast 代替服务端确认；各渠道展示目标值、已确认值及时间，人工配额不得写“实时”。

## 2. 共享 Demo 的每周重置

实现选择：每周一 03:00 Asia/Kuala_Lumpur 自动重置，另提供管理员手动重置；这是技术排程建议，不改变用户选择的每周周期。计划失败告警，不能每天重置。部署配置可调整具体时间并记录。

现有 Shop Demo 每日库存重置与 Demo Inventory 的周周期会冲突。接入 Demo Inventory 的 Shop 部署必须关闭本地库存每日重置，示例 SKU/占用/事件按共同重置流程处理；其他 Demo 业务数据是否保留由 Shop 自己的设计决定，不能未经设计删除会员历史/积分。

流程：

1. 校验实例固定模式为 demo，数据库账号仅能访问 Demo 库；生产实例不注册重置入口和任务，环境变量误配不能获得生产 DB 权限。
2. MySQL 持久记录 reset_id 与状态，获得单一重置执行权；Demo Inventory、Demo Shop 暂时拒绝示例新写入，页面显示重置中，保留预约入口。该短暂停止示例操作不作用真实站。
3. 停止旧周期消费者/模拟出站并等待处理中任务结束；持久状态超时则中止重置，不跳过仍在写入的作业。
4. 创建新 `demo_generation`，载入版本化 seed，清理或归档仅旧周期的示例预留、事件、幂等和余额；Demo Shop 关联示例订单按双方批准方案处理，不继续发送旧周期动作到新库存。
5. Inventory 和 Shop 均就绪并核对 seed 后启用同一 generation，重新开放示例写入。新页面/任务带服务端验证的 generation；旧浏览器提交和旧队列事件拒绝，不自动改成新周期重试。
6. 任一步失败保持两侧重置中、显示失败待办，由演示管理员恢复或按原 reset_id 续跑；不开放半套数据、不触碰真实实例，不把失败标为重置成功。

共享账号只能改当前周期的示例数据，不能修改种子、重置排程、外部连接或预约配置。验收须覆盖：同时修改时触发重置、队列迟到、双服务一侧失败、重复执行、生产入口不存在、独立商务 WhatsApp 预约不受影响。

## 3. 告警和运营处理

| 异常 | 通知与动作 |
| --- | --- |
| 需求缺口、配额超额、可能超卖、Inventory 临时不可用 | 严重，全天库存 Telegram + 后台；未确认每 15 分钟重复。本人 1 小时内决定继续销售或手动停售；无人备用，超时仅留记录。 |
| 授权失效/同步失败 | 后台按影响判级；有正在销售且库存无法确认/可能超卖时严重，其他普通问题每天 09:00–18:00 通知。 |
| 单纯人工 Shopee 核对逾期 | 仅后台，继续隔离人工份额；不发 Telegram、不自动停售/互借。 |
| 通知发送失败 | 持久重试并标记未送达；发送成功时间与确认时间分别保存，不能认为创建通知即已送达。 |

收到告警先看具体连接、SKU、缺口及最近核对，检查实物/已售占用/平台当前展示/未知写入。确认收到只停止重复提醒。管理者决定减配额或停售时先执行并核实来源渠道，记录原因；未确认目标发布结果不分配给其他渠道。结案须有数量及权限核对证据。

Shop 自己追踪真实售后首回 24 小时、发现故障缺货后联系顾客 48 小时、可履约已付款交运 48 小时、退货收到验收 48 小时、退款批准后发起 24 小时，均按已确认的每日自然计时规则。Inventory 不收顾客资料，不负责退款执行。

## 4. 备份与恢复方案

目标：RPO ≤15 分钟、RTO ≤4 小时、至少 30 天恢复窗口。备份不等于已可恢复，正式开放前必须演练。

建议在现有 MySQL 基础设施启用可验证的物理/逻辑全备 + binlog 时间点恢复。每日全备，连续变更归档目标不超过 5 分钟一次，给传输延迟留余量；保留覆盖最早恢复点之前的基线全备及其后所有日志，不能简单删除第 30 天的基础备份。实际 MySQL 版本、binlog 配置、备份工具、容量、远端备份存储尚待运维核实，未满足时真实上线闸门不通过。

- 加密备份到与生产数据库不同故障域的远端存储；密钥单独保管。仅同机目录、同 MySQL 实例或 Redis 缓存不满足。
- 监控最新成功全备、远端连续日志水位及恢复链完整性。日志落后超过 10 分钟严重提醒；目标为提前发现，不能靠一个定时表达式证明 RPO。
- 覆盖库存、SKU/映射、H/C、Q/T、预留、行计数、最小事件、幂等、审计和连接配置；加密平台令牌的解密密钥不写进数据库备份包，但须有独立可恢复方案。
- 共用 MySQL 时，恢复必须先在隔离实例重放至目标点，再导出/切换 Inventory 专属库；禁止直接回滚共享生产实例而影响 Shop 或其他项目。
- Shop 保留已发送成功以及待发送的最小库存事实和交付记录；Inventory PITR 可能丢失最近已确认处理的事件，恢复不能只重放 pending。按恢复水位重新发送相关事实，以业务唯一引用去重。
- 恢复旧库还可能恢复已撤销凭据或旧授权状态；开放服务前核对故障后的撤销/轮换记录，必要时轮换服务凭据和平台令牌。库存核对通过不等于旧凭据可以重新启用。
- 无法由外部重建的手工配置/盘点必须依赖备份和审计链；恢复窗口可能损失的部分由管理员核对重录并留依据，不声称 RPO 是零丢失。

### 4.1 恢复步骤与时间预算

| 故障后时段 | 步骤 | 证据 |
| --- | --- | --- |
| 0–30 分钟 | 负责人确认；保全当前库/日志，确定最后可信恢复点；人工决定渠道销售，不自动停售 | 决定记录、故障/备份水位、受影响 SKU。 |
| 30–150 分钟 | 隔离实例恢复全备与连续日志，核验结构/流水/幂等，保留故障副本 | 实际恢复点距故障 ≤15 分钟，校验结果。 |
| 150–210 分钟 | 核对恢复期所有 Shop 最小事件含已完成发送，补拉平台销售/人工核对，按引用重放 | 无重复占用/出库，缺口待办可见，配额和平台读数核对。 |
| 210–240 分钟 | 切换专属库存库，版本/健康检查，恢复可核对及新销售处理；管理员逐 SKU 决定恢复外部写入 | 实际 RTO、遗留异常及外部发布状态；未核实 SKU 不冒充全部恢复正常。 |

步骤预算是演练目标，不是现有已验证的恢复速度。恢复期间对现有可用 Inventory 若需封存写入，采用管理员明确维护操作并记录；故障中的 Shop 按已选择的持续收款路径持久排队，不把旧缓存视为确认。

上线前隔离演练模拟：一个备份窗口内完成付款/取消/出库、手工调整和配额转移；恢复后复算余额与订单行计数，重放成功和未成功事件。记录数据损失范围及各步骤耗时；关键恢复方式、备份工具或基础设施变更后重新演练，不以备份文件存在作为通过。

## 5. 迁移、部署失败和回退

1. 迁移任务先写字段/约束、旧数据来源、兼容旧应用、升级/回退影响；首期空库也要在临时 MySQL 验证。
2. 生产采用先加兼容结构、后切应用、最后另任务收紧/删除字段；部署前确认可恢复备份和迁移耗时。不能在日常自动部署里恢复整个数据库。
3. 应用失败可回退到兼容版本，数据库新增结构保留；破坏性 down migration 不自动执行。已有真实写入时，恢复旧库会丢失新销售，必须按故障恢复流程核对。
4. 回退不删除 inbox/outbox/幂等/流水；若旧版本不兼容当前结构，记录部署失败，人工处理，不能伪报回滚成功等于新版上线成功。
5. 线上健康检查必须返回实际运行 commit SHA；与 DEPLOY_SHA 不一致判失败。域名/DB 账号/Redis 空间/外部密钥分别按 Demo 和真实环境核对。

## 6. 尚需补齐的 Shop 决策

以下留在 Shop 设计闸门，不能由库存实现随意决定：未发货改地址跨配送地区后如何处理运费差额；故障/错发商品退货与保修的处理规则；真实优惠/积分、税费及相关文案；最终支付商和各方式退款例外。当前不生成正式法律政策或宣称合规验收完成。新加坡币种/汇率和跨境物流仍为后续。

## 7. 系统群部署、恢复和 Demo 补充

商品身份目录/基础库存账随单模块交付，Core 目录/账库与 Inventory 渠道/政策/审计库分别拥有数据。备份/恢复需覆盖同租户/池的联合版本、幂等和业务水位；只恢复 Inventory DB 不能恢复实物账，ERP/平台变更需对账重放，禁止按恢复中间状态向渠道新增发布。

公开 Demo 进入前登记邮箱/WhatsApp，真实线索写 Acuven CRM 或其独立待送达存储，不能进入共享模拟池；CRM 未可用时登记流程必须有持久移交设计，不直接丢数据。周重置仅模拟目录/账/Inventory/Shop 的同一 generation，不删联系方式和主动咨询记录、不自动营销。登记数据与共享体验权限分离。

组合门户一次登录后仍重验租户/角色/模块授权；单模块本地登录与业务运行不依赖门户在线。外部客户 SaaS、托管专属和自托管分别验收；平台运营身份默认无业务明细权，限时支持由客户批准并留审计。旧 Acuven 自营本人告警安排不能代替对外 24×7 人工支持和值班证据。
